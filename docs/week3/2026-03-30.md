## 파트 1 — 코딩테스트

### 🟡 소수 찾기 (`week3/PrimeNumbers.java`)

**문제**

- 1부터 n 사이의 소수의 개수를 반환

**핵심 아이디어 — 에라토스테네스의 체**

- 2부터 √N까지 순회하며 각 소수의 배수를 제거
- `j = i * i` 부터 시작 → i보다 작은 배수는 이전 i에서 이미 처리됨

```java
package week3;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.util.Arrays;

public class PrimeNumbers {
  public static void main(String[] args) throws IOException {
    BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
    int n = Integer.parseInt(br.readLine());

    boolean[] isPrime = new boolean[n + 1];
    Arrays.fill(isPrime, true);

    isPrime[0] = isPrime[1] = false;

    for (int i = 2; i * i <= n; i++) {
      if (isPrime[i]) {
        // i*i 미만의 배수는 이미 이전 단계에서 처리됨
        for (int j = i * i; j <= n; j += i) {
          isPrime[j] = false;
        }
      }
    }

    int count = 0;
    for (int i = 2; i <= n; i++) {  // 1은 소수가 아님을 명시적으로 표현
      if (isPrime[i]) count++;
    }

    System.out.println(count);
  }
}
```

**복잡도 분석**

| 구분 | 복잡도            | 이유                                        |
|----|----------------|-------------------------------------------|
| 시간 | O(N log log N) | 각 소수 p마다 N/p번 배수 제거, 소수의 역수 합 = log log N |
| 공간 | O(N)           | boolean 배열 크기 N+1                         |

**개선 포인트**

- 카운트 루프 시작을 `i = 1` → `i = 2`로 변경
- `isPrime[1] = false` 처리와 일관성 유지, 코드 가독성 향상

## 파트 2 — CS 개념: 네트워크

### HTTP vs HTTPS

#### HTTP (HyperText Transfer Protocol)

- 클라이언트와 서버가 데이터를 주고받는 **통신 규약**
- 데이터를 **평문**으로 전송 → 중간에 가로채면 내용 노출 🔓

```
클라이언트 ── GET /index.html ──▶ 서버
클라이언트 ◀── 200 OK + HTML ──── 서버
```

#### HTTPS = HTTP + TLS

- TLS(Transport Layer Security) 암호화 적용
- 평문 대신 암호화된 데이터 전송 🔐

**TLS가 보장하는 3가지**

| 역할  | 설명                       |
|-----|--------------------------|
| 암호화 | 데이터를 암호화해서 중간에 가로채도 못 읽음 |
| 인증  | 서버가 진짜 서버인지 확인 (SSL 인증서) |
| 무결성 | 데이터가 중간에 변조되지 않았음을 보장    |

#### TLS Handshake 흐름

```
클라이언트                          서버
    |── 1. ClientHello ────────────▶|  암호화 방식 제안
    |◀── 2. ServerHello ────────────|  방식 확정 + 인증서 전달
    |── 3. 인증서 검증 (클라이언트) ──|  CA 목록과 대조
    |── 4. 세션키 교환 ─────────────▶|  암호화 키 합의
    |◀══════ 5. 암호화 통신 ═════════|  🔐
```

> ⚠️ 인증서 검증 주체 = **클라이언트** (내가 들어가는 사이트가 진짜인지 내가 확인)

### TCP 3-way Handshake

**왜 필요한가?**

- 데이터 전송 전 **양방향 통신 가능 여부** 확인

```
클라이언트 ── 1. SYN ───────────▶ 서버   "연결 요청"
클라이언트 ◀── 2. SYN-ACK ──────── 서버   "수락 + 역방향 연결 요청"
클라이언트 ── 3. ACK ───────────▶ 서버   "수락 확인"
              ══════ 데이터 전송 ══════ 🚀
```

| 단계 | 이름      | 의미                            |
|----|---------|-------------------------------|
| 1  | SYN     | 클라이언트 → 서버: 연결 요청             |
| 2  | SYN-ACK | 서버 → 클라이언트: 요청 수락 + 역방향 연결 요청 |
| 3  | ACK     | 클라이언트 → 서버: 수락 확인             |

**왜 2번이 아닌 3번인가?**
> 2번(SYN → SYN-ACK)만 하면 서버는 자신의 응답이 클라이언트에게 전달됐는지 확인할 수 없음
> → 최소 3번이어야 양방향 확인 완료

---

### TCP 4-way Handshake (연결 종료)

```
클라이언트 ── 1. FIN ───────────▶ 서버   "다 보냈어, 끊을게"
클라이언트 ◀── 2. ACK ────────── 서버   "알겠어, 잠깐만"
클라이언트 ◀── 3. FIN ────────── 서버   "나도 다 보냈어, 끊을게"
클라이언트 ── 4. ACK ───────────▶ 서버   "확인, 끊자"
```

**3-way와 다른 이유**
> 서버가 아직 보낼 데이터가 남아있을 수 있어서
> ACK와 FIN을 한 번에 보내지 못하고 두 번으로 나뉨

---

### TCP vs UDP

| 구분       | TCP   | UDP  |
|----------|-------|------|
| 연결       | 필요 O  | 필요 X |
| 순서 보장    | O     | X    |
| 손실 시 재전송 | O     | X    |
| 속도       | 느림    | 빠름   |
| 비유       | 전화 통화 | 편지   |

**실제 사용 예시**

| 프로토콜 | 사용처               | 이유              |
|------|-------------------|-----------------|
| TCP  | HTTP/HTTPS, 파일 전송 | 데이터 손실 허용 안 됨   |
| UDP  | 영상통화, 게임, DNS     | 속도 중요, 약간 손실 허용 |

**DNS가 UDP를 쓰는 이유**
> 요청/응답 데이터가 매우 작고 속도가 중요하기 때문에
> 연결 수립 오버헤드(3-way Handshake) 없이 바로 전송하는 UDP 사용

## 면접 예상 질문

**Q1. HTTP와 HTTPS의 차이를 설명해주세요.**
> HTTP는 데이터를 평문으로 전송하지만, HTTPS는 TLS 암호화를 적용합니다.
> TLS Handshake를 통해 암호화 방식을 협의하고, 클라이언트가 서버의 인증서를 검증한 뒤
> 세션키를 교환해 암호화 통신을 시작합니다. TLS는 암호화 / 인증 / 무결성을 보장합니다.

**Q2. TCP 3-way Handshake를 설명해주세요.**
> TCP는 데이터 전송 전 양방향 통신 가능 여부를 확인합니다.
> 클라이언트가 SYN으로 연결을 요청하고, 서버가 SYN-ACK로 수락 및 역방향 연결을 요청하고,
> 클라이언트가 ACK로 확인하는 3단계가 필요합니다.
> 2번으로는 서버가 자신의 응답이 전달됐는지 확인할 수 없기 때문에 최소 3번이 필요합니다.

**Q3. TCP와 UDP의 차이와 각각의 사용 사례를 말해주세요.**
> TCP는 연결 지향적으로 순서 보장과 재전송을 지원해 신뢰성이 높지만 속도가 느립니다.
> UDP는 비연결 지향적으로 빠르지만 신뢰성이 낮습니다.
> TCP는 HTTP, 파일 전송처럼 데이터 손실이 허용되지 않는 곳에,
> UDP는 영상통화, 게임, DNS처럼 속도가 중요한 곳에 사용합니다.

**Q4. DNS는 왜 UDP를 사용하나요?**
> DNS 요청/응답은 데이터 크기가 매우 작고 속도가 중요합니다.
> TCP를 사용하면 매 요청마다 3-way Handshake 오버헤드가 발생하므로
> 연결 수립 없이 바로 전송하는 UDP를 사용합니다.
