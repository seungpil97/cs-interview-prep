## 파트 1 — 코딩테스트

### 문제
```
패키지: week2
클래스명: ValidParenthesesCombinations

n쌍의 괄호로 만들 수 있는 모든 올바른 괄호 조합을 반환하세요.

입력: int n
출력: List<String>

예시)
n=1 → ["()"]
n=2 → ["(())", "()()"]
n=3 → ["((()))", "(()())", "(())()", "()(())", "()()()"]
```

### 최종 풀이 코드

```java
package week2;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;

public class ValidParenthesesCombinations {

  public static void main(String[] args) throws IOException {
    BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
    int n = Integer.parseInt(br.readLine());

    StringBuilder sb = new StringBuilder();
    generate(0, 0, n, sb);
  }

  private static void generate(int open, int close, int n, StringBuilder sb) {

    if (open == n && close == n) {
      System.out.println(sb);
      return;
    }

    if (open < n) {
      sb.append("(");
      generate(open + 1, close, n, sb);
      sb.deleteCharAt(sb.length() - 1);  // 백트래킹
    }
    if (close < open) {
      sb.append(")");
      generate(open, close + 1, n, sb);
      sb.deleteCharAt(sb.length() - 1);  // 백트래킹
    }
  }
}
```

### 핵심 아이디어

- `(` 를 붙일 수 있는 조건: `open < n`
- `)` 를 붙일 수 있는 조건: `close < open`
- 종료 조건: `open == n && close == n`
- 재귀 호출 전 상태 변경 → 호출 후 원복 = **백트래킹**

### 백트래킹 동작 원리

```
sb.append("(");          // 1. 붙이고 (발자국 남기기)
generate(open+1, ...);   // 2. 재귀 탐색
sb.deleteCharAt(...);    // 3. 돌아오면 지움 (발자국 지우기)
```

n=2 탐색 트리:
```
generate(0,0,2,"")
  ├─ append("(") → "("
  │   ├─ append("(") → "(("
  │   │   └─ append(")") → "(()"
  │   │       └─ append(")") → "(())" ✅ 출력
  │   └─ append(")") → "()"
  │       └─ append("(") → "()("
  │           └─ append(")") → "()()" ✅ 출력
```

### 복잡도 분석

| | 복잡도 | 이유 |
|--|--------|------|
| 시간 | O(4^n) | 깊이 2n, 매 단계 최대 2분기 → 정확히는 카탈란 수 O(4^n / √n) |
| 공간 | O(n) | 재귀 스택 깊이 2n + StringBuilder 크기 2n |

> 면접 포인트: "매 단계에서 최대 2가지 선택을 하고, 깊이가 2n이므로 O(4^n)으로 볼 수 있습니다."

### String vs StringBuilder 비교

| | String | StringBuilder |
|--|--------|---------------|
| 방식 | `current + "("` → 매번 새 객체 생성 | `sb.append()` → 같은 객체 수정 |
| 되돌리기 | 자동 (불변) | `deleteCharAt()` 직접 호출 |
| 메모리 | O(n) 객체 매번 생성 | O(n) 하나 재사용 |

### 오늘 배운 키워드
- 백트래킹 (Backtracking)
- 카탈란 수 (Catalan Number)
- StringBuilder + deleteCharAt 패턴

## 파트 2 — CS 면접 Q&A (Week 2 전체 복습)

### OS — 가상메모리 / 페이징 / TLB / 페이지 폴트 / 스래싱

#### 가상 메모리
> 각 프로세스에게 독립된 가상 주소 공간을 제공하는 기법.
> 물리 메모리 크기에 상관없이 프로세스가 메모리를 독점하는 것처럼 동작.
> 내부적으로 페이징 기법으로 가상 주소를 물리 주소로 변환.
> 실제로 필요한 페이지만 물리 메모리에 올리고 나머지는 디스크(스왑)에 저장.

#### 페이지 폴트
> 프로세스가 요청한 페이지가 물리 메모리에 없을 때 발생하는 **인터럽트**.

처리 순서:
1. CPU가 페이지 폴트 인터럽트 발생
2. OS가 디스크(스왑 영역)에서 해당 페이지 확인
3. 빈 프레임 있으면 로드, 없으면 페이지 교체 알고리즘(LRU/FIFO)으로 희생 페이지 선택
4. 페이지 테이블 업데이트 후 프로세스 재개

#### 스래싱 (Thrashing)
> 페이지 폴트가 과도하게 발생해서 프로세스가 실제 작업보다 페이지 교체에 더 많은 시간을 소비하는 현상

발생 원인:
```
프로세스 수 증가 → 프레임 수 감소 → 페이지 폴트 빈발 → CPU 이용률 급락
```

해결 방법:
- 프로세스 수 줄이기
- 워킹셋 알고리즘 (최근 자주 사용한 페이지 묶음 보장)
- 물리 메모리 증설

#### TLB (Translation Lookaside Buffer)
> 페이지 테이블 접근 속도를 높이기 위한 **하드웨어 캐시**

| 상황 | 동작 |
|------|------|
| TLB 히트 | TLB에서 바로 변환 → 빠름 |
| TLB 미스 | 페이지 테이블에서 찾고 TLB에 저장 → 느림 |

### JVM — 힙 구조 / GC / STW / G1 GC

#### JVM 힙 구조

```
Young Generation
  ├─ Eden      ← 새 객체 생성
  ├─ Survivor0 (S0)
  └─ Survivor1 (S1)  ← S0/S1 중 하나는 항상 비어있어야 함
Old Generation       ← age 임계값(15) 초과 시 Promotion
Metaspace            ← 클래스 메타데이터 (Java 8부터 PermGen 대체)
```

#### GC 동작 흐름

```
1. 객체 생성 → Eden
2. Eden 가득 참 → Minor GC 발생
3. 살아남은 객체 → S0 또는 S1 이동, age++
4. age >= 15 → Old Generation으로 Promotion
5. Old 가득 참 → Major GC 발생 → STW (Stop The World)
```

#### G1 GC

기존 GC와 차이:
| | 기존 GC | G1 GC |
|--|--------|-------|
| 영역 구조 | Eden/Survivor/Old 고정 크기 | 동일 크기 Region으로 분할 |
| 역할 | 고정 | 동적으로 Eden/Survivor/Old/Humongous 역할 부여 |
| STW | Old 전체 수집 → 길다 | 가비지 많은 Region 우선 수집 → 짧고 예측 가능 |
| 기본 채택 | Java 8 이전 | Java 9부터 기본 GC |

> **Humongous Region**: Region 크기의 50% 초과하는 큰 객체를 저장하는 특수 영역

## OS — 가상메모리 / 페이징 / TLB / 페이지 폴트 / 스래싱

---

### Q1. 가상 메모리가 무엇인가요?

> 가상 메모리란 각 프로세스에게 독립된 가상 주소 공간을 제공하는 기법입니다.
> 물리 메모리 크기에 상관없이 프로세스가 마치 메모리를 독점하는 것처럼 동작할 수 있게 해줍니다.
> 내부적으로는 페이징 기법을 통해 가상 주소를 물리 주소로 변환하며,
> 실제로 필요한 페이지만 물리 메모리에 올리고 나머지는 디스크(스왑)에 둡니다.

**꼬리질문 대비:**
- Q. 왜 각 프로세스에 독립된 주소 공간을 주나요?
  - A. 프로세스 간 메모리 침범을 막아 **격리성과 보안**을 보장하기 위해서입니다.

---

### Q2. 페이지 폴트 발생 시 처리 과정을 설명하세요.

> 페이지 폴트란 프로세스가 요청한 페이지가 물리 메모리에 없을 때 발생하는 인터럽트입니다.
> 발생하면 OS가 개입해 다음 순서로 처리합니다.
> 1. CPU가 페이지 폴트 인터럽트 발생
> 2. OS가 디스크(스왑 영역)에서 해당 페이지 확인
> 3. 물리 메모리에 빈 프레임이 있으면 로드, 없으면 페이지 교체 알고리즘(LRU/FIFO)으로 희생 페이지 선택
> 4. 페이지 테이블 업데이트 후 프로세스 재개

**꼬리질문 대비:**
- Q. 페이지 교체 알고리즘 종류는?
  - A. FIFO(먼저 들어온 페이지 교체), LRU(가장 오래 안 쓴 페이지 교체), LFU(가장 적게 쓴 페이지 교체)가 있습니다. 실제로는 LRU를 많이 사용합니다.

---

### Q3. 스래싱이 무엇이고 어떻게 해결하나요?

> 페이지 폴트가 과도하게 발생해서 프로세스가 실제 작업보다 페이지 교체에 더 많은 시간을 소비하는 현상입니다.
> 프로세스 수가 증가할수록 각 프로세스에 할당되는 프레임 수가 줄어들어 페이지 폴트가 빈번해지고,
> CPU가 페이지 교체만 반복하면서 CPU 이용률이 급격히 하락합니다.
> 해결책으로는 프로세스 수를 줄이거나, 워킹셋 알고리즘을 적용하거나, 물리 메모리를 증설합니다.

**꼬리질문 대비:**
- Q. 워킹셋 알고리즘이 뭔가요?
  - A. 프로세스가 최근 일정 시간 동안 자주 사용한 페이지 묶음을 보장하는 알고리즘입니다. 이 페이지들을 메모리에 유지해 페이지 폴트를 줄입니다.

---

### Q4. TLB가 무엇인가요?

> TLB(Translation Lookaside Buffer)는 페이지 테이블 접근 속도를 높이기 위한 하드웨어 캐시입니다.
> 가상 주소를 물리 주소로 변환할 때 먼저 TLB를 확인하고,
> 있으면(TLB 히트) 바로 변환하고, 없으면(TLB 미스) 페이지 테이블에서 찾고 TLB에 저장합니다.
> CPU 안에 위치해 매우 빠르게 동작합니다.

**꼬리질문 대비:**
- Q. TLB 미스가 자주 발생하면 어떻게 되나요?
  - A. 매번 페이지 테이블까지 접근해야 해서 메모리 접근이 2번 발생하고 성능이 저하됩니다.

## JVM — 힙 구조 / GC / STW / G1 GC

---

### Q5. JVM 힙 구조를 설명하세요.

> JVM 힙은 Young Generation과 Old Generation으로 나뉩니다.
> Young Generation은 Eden, S0, S1으로 구성되며 새로운 객체는 Eden에 생성됩니다.
> Eden이 가득 차면 Minor GC가 발생하고, 살아남은 객체는 Survivor(S0/S1)로 이동하며 age가 증가합니다.
> S0과 S1 중 하나는 항상 비어있어야 하며, age가 임계값(기본 15)을 초과하면 Old Generation으로 Promotion됩니다.
> 클래스 메타데이터는 Java 8부터 PermGen 대신 Metaspace에 저장됩니다.

**꼬리질문 대비:**
- Q. Metaspace가 PermGen과 다른 점은?
  - A. PermGen은 힙 내 고정 크기 영역이라 OOM이 자주 발생했습니다. Metaspace는 네이티브 메모리를 사용해 크기가 동적으로 조정됩니다.

---

### Q6. Minor GC와 Major GC의 차이는?

> Minor GC는 Young Generation(Eden, Survivor)을 대상으로 발생하며 빠르게 처리됩니다.
> Major GC(Full GC)는 Old Generation까지 포함해 전체 힙을 대상으로 발생하며,
> STW(Stop The World) 시간이 길어 애플리케이션이 멈추는 것처럼 보입니다.

**꼬리질문 대비:**
- Q. STW를 줄이려면 어떻게 하나요?
  - A. G1 GC나 ZGC처럼 STW 시간을 최소화하도록 설계된 GC를 사용합니다.

---

### Q7. G1 GC가 기존 GC와 다른 점은?

> G1 GC는 힙을 고정 영역이 아닌 동일한 크기의 Region으로 나눕니다.
> 각 Region은 동적으로 Eden, Survivor, Old, Humongous 역할을 맡습니다.
> 기존 GC는 Old 전체를 수집해 STW가 길었지만,
> G1은 가비지가 많은 Region을 우선 수집해 STW 시간을 짧고 예측 가능하게 유지합니다.
> Java 9부터 기본 GC로 채택되었습니다.

**꼬리질문 대비:**
- Q. Humongous Region이 무엇인가요?
  - A. Region 크기의 50%를 초과하는 큰 객체를 저장하는 특수 영역입니다. 일반 GC 사이클에서 별도로 관리됩니다.

## 코딩테스트 — 백트래킹

---

### Q8. 백트래킹이란 무엇인가요?

> 백트래킹은 재귀로 가능한 모든 경우를 탐색하되,
> 재귀 호출 전에 상태를 변경하고 호출이 끝나면 원래 상태로 복원하는 기법입니다.
> 불필요한 경로를 가지치기(pruning)해서 완전 탐색보다 효율적으로 동작합니다.

**꼬리질문 대비:**
- Q. DFS와 백트래킹의 차이는?
  - A. DFS는 탐색 방식이고, 백트래킹은 DFS에서 상태 복원을 추가한 개념입니다. 백트래킹은 조건에 맞지 않는 경로를 조기에 차단해 탐색 범위를 줄입니다.

---

### Q9. StringBuilder를 백트래킹에 사용할 때 주의할 점은?

> StringBuilder는 가변 객체이기 때문에 재귀 호출 간 공유됩니다.
> 따라서 append로 문자를 추가했다면, 재귀가 끝난 후 반드시 deleteCharAt으로 원복해야 합니다.
> String을 사용하면 불변이라 자동으로 원복되지만, 매 호출마다 새 객체가 생성되어 메모리 효율이 낮습니다.
