## 코딩테스트 — LongestCommonPrefix

### 문제

문자열 배열이 주어졌을 때 모든 문자열의 공통 접두사(prefix)를 반환하세요.
없으면 `""` 반환.

```
["flower", "flow", "flight"] → "fl"
["dog", "racecar", "car"]   → ""
["ab", "a"]                 → "a"
["a"]                       → "a"
```

### 풀이 코드

```java
package week2;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;

public class LongestCommonPrefix {
  public static void main(String[] args) throws IOException {
    BufferedReader br = new BufferedReader(new InputStreamReader(System.in));

    String[] strs = br.readLine().split(" ");

    String prefix = strs[0];

    for (int i = 1; i < strs.length; i++) {
      while (!strs[i].startsWith(prefix)) {
        prefix = prefix.substring(0, prefix.length() - 1);
        if (prefix.isEmpty()) break;
      }
    }
    System.out.println(prefix);
  }
}
```

### 핵심 아이디어

- `prefix = strs[0]` 으로 초기값 설정
- 각 문자열과 비교해 `startsWith()` 가 false면 prefix를 뒤에서 한 글자씩 제거
- `prefix.isEmpty()` 시 break로 조기 종료 ← **의도를 명시하는 코드**
- `"".startsWith("")` 는 Java에서 항상 true이므로 무한루프는 없지만 명시적 처리 권장

### 동작 추적 — `["flower", "flow", "flight"]`

| 단계  | 비교 문자열   | prefix 변화             | 결과     |
|-----|----------|-----------------------|--------|
| i=1 | "flow"   | flower → flowe → flow | "flow" |
| i=2 | "flight" | flow → flo → fl       | "fl"   |

### 복잡도 분석

|    | 복잡도    | 이유                                                           |
|----|--------|--------------------------------------------------------------|
| 시간 | O(N*M) | 외부 루프 N번 × 내부 while 최대 M번                                    |
| 공간 | O(M)   | prefix 변수가 최대 M 길이의 String 보관, `substring()`은 새 String 객체 생성 |

> Java 7 이후 `substring()`은 새 String 객체를 생성하므로 공간복잡도 분석 시 String 길이도 고려해야 한다.

## CS 개념 — 가상메모리 / 페이징 / TLB / 페이지 폴트 / JVM / GC / G1 GC

### 가상메모리 (Virtual Memory)

**왜 필요한가?**

- 물리 메모리의 한계를 극복하기 위해 등장한 메모리 관리 기법
- 각 프로세스에게 독립된 가상 주소 공간을 제공
- 당장 필요한 페이지만 물리 메모리에 올리고 나머지는 디스크(스왑 영역)에 보관

**효과**

| 효과           | 설명                         |
|--------------|----------------------------|
| 물리 메모리 초과 실행 | 물리 메모리보다 큰 프로세스들을 동시 실행 가능 |
| 메모리 보호       | 프로세스 간 메모리 침범 방지           |

---

### 페이징 (Paging)

**개념**

- 가상 주소 공간과 물리 메모리를 **고정 크기 단위**로 나눠서 매핑하는 기법

| 용어      | 설명                                  |
|---------|-------------------------------------|
| 페이지     | 가상 주소를 고정 크기로 나눈 단위 (일반적으로 4KB)     |
| 프레임     | 물리 메모리를 같은 크기로 나눈 단위                |
| 페이지 테이블 | 페이지 → 프레임 매핑 정보를 저장하는 테이블 (RAM에 저장) |

```
가상 주소 공간          물리 메모리
┌──────────┐           ┌──────────┐
│ 페이지 0  │ ───────→  │ 프레임 3  │
│ 페이지 1  │ ───────→  │ 프레임 7  │
│ 페이지 2  │ ───────→  │ 디스크    │  ← 아직 물리 메모리에 없는 경우
│ 페이지 3  │ ───────→  │ 프레임 1  │
└──────────┘           └──────────┘
```

> 가상 주소는 연속적으로 보이지만 물리 메모리에는 불연속적으로 배치 가능

---

### TLB (Translation Lookaside Buffer)

**왜 필요한가?**

- 페이지 테이블은 RAM에 저장 → 주소 변환 시 메모리를 2번 접근해야 함
- TLB는 최근 사용한 페이지-프레임 매핑을 CPU 가까이에 캐시

```
CPU → TLB 확인
    ↓ TLB 히트 → 바로 물리 주소 변환 (빠름)
    ↓ TLB 미스 → 메모리에서 페이지 테이블 조회 (느림)
```

|         | 저장 위치     | 속도    |
|---------|-----------|-------|
| 페이지 테이블 | RAM       | 느림    |
| TLB     | CPU 내부 캐시 | 매우 빠름 |

> 컨텍스트 스위칭 시 프로세스마다 주소 공간이 달라 TLB 플러시 발생

---

### 페이지 폴트 (Page Fault)

**개념**

- CPU가 접근하려는 페이지가 물리 메모리에 없을 때 발생하는 인터럽트

**처리 순서**

```
1. CPU가 가상 주소 접근
2. 페이지 테이블 확인 → 물리 메모리에 없음 (페이지 폴트 발생)
3. OS가 디스크(스왑 영역)에서 해당 페이지 찾기
4. 물리 메모리에 빈 프레임 확보 (없으면 기존 페이지 스왑 아웃)
5. 디스크 → 물리 메모리로 페이지 로드
6. 페이지 테이블 업데이트
7. CPU 재실행
```

> 디스크 접근이 발생하기 때문에 매우 느림
> 페이지 폴트가 과도하게 발생하면 **스래싱(Thrashing)** 으로 이어질 수 있음

---

### JVM 힙 구조

```
┌─────────────────────────────────────────────┐
│               Young Generation               │
│  ┌──────────┬──────────────┬──────────────┐  │
│  │  Eden    │  Survivor 0  │  Survivor 1  │  │
│  └──────────┴──────────────┴──────────────┘  │
├─────────────────────────────────────────────┤
│               Old Generation                 │
├─────────────────────────────────────────────┤
│               Metaspace (Java 8+)            │
└─────────────────────────────────────────────┘
```

**객체 이동 흐름**

```
new 객체 생성 → Eden
    ↓ Eden 꽉 참 → Minor GC
살아남은 객체 → S0 ↔ S1 (Minor GC마다 번갈아 이동, age 증가)
    ↓ age 임계값 초과 (기본 15)
Old Generation
    ↓ Old 꽉 참 → Major GC
```

> S0, S1은 항상 하나만 사용 중 — 나머지 하나는 비어있음

---

### GC & STW

**GC(Garbage Collection)**

- 더 이상 참조되지 않는 객체를 자동으로 메모리에서 해제하는 JVM의 메모리 관리 기법

|       | Minor GC         | Major GC       |
|-------|------------------|----------------|
| 발생 위치 | Young Generation | Old Generation |
| 속도    | 빠름               | 느림             |
| STW   | 짧음               | 길음             |
| 빈도    | 자주               | 가끔             |

**STW(Stop The World)**

- GC 실행 중 GC 스레드를 제외한 모든 애플리케이션 스레드 일시 정지
- STW 시간이 길어지면 사용자 응답 지연으로 이어짐
- **STW 시간 최소화 = GC 튜닝의 핵심**

---

### G1 GC

**기존 GC vs G1 GC**

```
기존 GC: [ ----Young(고정)---- | --------Old(고정)-------- ]

G1 GC:  [ E ][ E ][ S ][ O ][ E ][ O ]
        [ O ][ E ][ S ][ E ][ O ][ E ]
        (Region 단위로 동적 관리)
```

|          | 기존 GC | G1 GC                       |
|----------|-------|-----------------------------|
| 영역 크기    | 고정    | 동적 (Region 단위)              |
| STW 예측   | 어려움   | 가능 (`-XX:MaxGCPauseMillis`) |
| 적합한 힙 크기 | 소~중형  | 대형 (4GB 이상)                 |

> Java 9부터 기본 GC로 채택
> H(Humongous) Region — Region 크기 50% 이상인 큰 객체를 별도 저장
> 이름이 G1(Garbage First)인 이유 — 가비지가 많은 Region을 우선 수거

## 면접 예상 질문

**Q1. 가상메모리란 무엇이고 왜 필요한가요?**
> 가상메모리는 물리 메모리의 한계를 극복하기 위해 등장한 메모리 관리 기법입니다. 각 프로세스에게 독립된 가상 주소 공간을 제공하여, 실제
> 물리 메모리 크기와 상관없이 더 많은 프로세스를 동시에 실행할 수 있게 해줍니다. 당장 필요한 페이지만 물리 메모리에 올리고 나머지는 디스크(
> 스왑 영역)에 두기 때문에 가능하며, 프로세스 간 메모리 침범을 방지하는 보호 효과도 있습니다.

**Q2. TLB란 무엇이고 왜 필요한가요?**
> TLB(Translation Lookaside Buffer)는 페이지 테이블 조회 속도를 높이기 위한 CPU 내부 캐시입니다. 페이지
> 테이블은 RAM에 저장되어 있어 주소 변환 시마다 메모리를 2번 접근해야 하는 오버헤드가 발생합니다. TLB는 최근 사용한 페이지-프레임 매핑을
> CPU 가까이에 저장해 이 오버헤드를 줄여줍니다. TLB에 원하는 매핑이 있으면 TLB 히트, 없으면 TLB 미스라고 하며, 컨텍스트 스위칭
> 시에는 TLB 플러시가 발생합니다.

**Q3. 페이지 폴트란 무엇인가요?**
> 페이지 폴트란 CPU가 접근하려는 페이지가 물리 메모리에 없을 때 발생하는 인터럽트입니다. 발생 시 OS가 디스크(스왑 영역)에서 해당
> 페이지를 찾아 물리 메모리에 로드하고, 페이지 테이블을 업데이트한 뒤 CPU가 명령을 재실행합니다. 디스크 접근이 발생하기 때문에 성능에 큰
> 영향을 주며, 페이지 폴트가 과도하게 발생하면 스래싱으로 이어질 수 있습니다.

**Q4. GC란 무엇이고 STW가 왜 문제인가요?**
> GC(Garbage Collection)는 더 이상 참조되지 않는 객체를 자동으로 메모리에서 해제하는 JVM의 메모리 관리 기법입니다.
> Minor GC는 Young Generation이 꽉 찰 때 빠르게 실행되고, Major GC는 Old Generation이 꽉 찰 때 발생하며
> 상대적으로 오래 걸립니다. GC 실행 중에는 STW(Stop The World)가 발생해 GC 스레드를 제외한 모든 애플리케이션 스레드가 일시
> 정지됩니다. 이 시간이 길어지면 사용자 응답 지연으로 이어지기 때문에 STW 시간 최소화가 GC 튜닝의 핵심입니다.

**Q5. G1 GC란 무엇이고 기존 GC와 어떤 차이가 있나요?**
> G1 GC는 Java 9부터 기본 GC로 채택된 가비지 컬렉터로, 기존 GC의 긴 STW 문제를 해결하기 위해 등장했습니다. 기존 GC는
> 힙을 Young/Old로 고정 분할했지만, G1 GC는 힙을 동일한 크기의 Region으로 나누고 동적으로 Eden/Survivor/Old
> 역할을 부여합니다. 가비지가 많은 Region을 우선적으로 수거(Garbage First)하고, `-XX:MaxGCPauseMillis`로
> STW 목표 시간을 설정할 수 있어 대용량 힙에서 유리합니다.
