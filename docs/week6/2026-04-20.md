## 1. 영속성 컨텍스트란?

JPA가 엔티티를 DB에 바로 저장하지 않고 메모리에 먼저 올려두는 공간.
여기서 1차 캐시, 변경 감지, 쓰기 지연이 동작한다.

**왜 필요한가?**
매번 DB에 접근하면 느리니까, 트랜잭션 동안은 메모리에 캐싱해두고 재사용한다.

```
조회 요청
    → 1차 캐시에 있으면? → 거기서 반환 (DB 접근 X)
    → 없으면? → DB 접근 → 1차 캐시에 저장 → 반환
```

> ⚠️ 1차 캐시는 트랜잭션이 끝나면 사라진다. 영구 캐시가 아님.

---

## 2. 핵심 기능 4가지

### 2-1. 1차 캐시

같은 트랜잭션 안에서 동일 ID를 두 번 조회하면 두 번째는 DB 접근 없이 반환.

```java
Reservation r1 = reservationRepository.findById(1L); // DB 조회
Reservation r2 = reservationRepository.findById(1L); // 1차 캐시 반환 (DB 접근 X)
r1 == r2 // true
```

### 2-2. Dirty Checking (변경 감지)

엔티티를 처음 조회할 때 스냅샷을 찍어둔다.
트랜잭션 커밋 직전 스냅샷과 현재 상태를 비교해서 달라진 게 있으면 자동 UPDATE.

```
findById() 호출 → 1차 캐시 저장 + 스냅샷 찍음
    ↓
reservation.cancel() 호출 → 상태 변경
    ↓
커밋 직전 → 스냅샷이랑 비교 → 다르면 자동 UPDATE 실행
```

→ `save()` 를 명시적으로 안 써도 DB 반영이 된다.

### 2-3. 쓰기 지연 (Write-Behind)

INSERT/UPDATE를 바로 실행하지 않고 쓰기 지연 SQL 저장소에 모아뒀다가
flush 시점에 한꺼번에 전송한다.

### 2-4. Flush 시점

| 시점               | 설명                      |
|------------------|-------------------------|
| 트랜잭션 커밋          | 가장 일반적인 케이스             |
| JPQL 쿼리 실행 직전    | DB 정합성을 맞추기 위해 자동 flush |
| 명시적 `em.flush()` | 강제 실행                   |

**JPQL 전 자동 flush 이유**
DB에 반영 안 된 변경사항이 있는데 바로 조회하면 결과가 틀리니까,
먼저 flush해서 DB에 반영하고 조회한다.

```java
@Transactional
public void someMethod() {
    reservation.cancel();            // 쓰기 지연 저장소에 대기
    reservationRepository.findAll(); // JPQL 실행 직전 자동 flush → 취소된 상태로 조회됨
}
```

## 3. OSIV (Open Session In View)

### OSIV true (Spring Boot 기본값)

영속성 컨텍스트가 HTTP 응답 완료 시점까지 살아있음.
트랜잭션 = 영속성 컨텍스트 = 커넥션이 같이 움직이므로
**커넥션을 HTTP 응답까지 점유**한다.

```
HTTP 요청 시작 → 커넥션 획득
    → Controller → Service → Repository
    → JSON 직렬화
HTTP 응답 완료 → 그제서야 커넥션 반납
```

### OSIV false (실무 권장)

트랜잭션이 끝나는 순간 커넥션 즉시 반납.

```
HTTP 요청 시작
    → Controller → Service → Repository
    → 트랜잭션 종료 → 커넥션 즉시 반납
    → JSON 직렬화
HTTP 응답 완료
```

**주의:** OSIV false면 트랜잭션 밖에서 Lazy Loading 불가.
→ `LazyInitializationException` 발생
→ Service 안에서 필요한 데이터를 다 로딩해서 DTO로 변환해서 반환해야 한다.

```yaml
# 실무 권장 설정
spring.jpa.open-in-view=false
```

## 4. 현재 프로젝트 연결 (TASK-011, TASK-017)

### EventRepository — DTO 프로젝션 사용

```java
@Query("""
    select new com.pil97.ticketing.event.application.dto.EventSummaryQueryResult(
        e.id, e.name, e.venue, min(s.showAt), e.status
    )
    from Event e
    join Showtime s on s.event = e
    group by e.id, e.name, e.venue, e.status
    order by min(s.showAt) asc
""")
List<EventSummaryQueryResult> findEventSummaries();
```

|                | Entity 조회   | DTO 프로젝션 |
|----------------|-------------|----------|
| 영속성 컨텍스트 관리    | O           | X        |
| Dirty Checking | O           | X        |
| 성능             | 스냅샷 오버헤드 있음 | 빠름       |
| 용도             | 수정이 필요한 경우  | 읽기 전용    |

`findEventSummaries()` 는 변경이 필요 없는 읽기 전용 조회이므로
DTO 프로젝션을 사용한 것은 좋은 선택.

## 5. 장애 가능성

### OSIV + 커넥션 풀 고갈

OSIV true + 고트래픽 상황에서 커넥션 점유 시간이 길어져 풀 고갈 위험.

**숫자 기반 시나리오**

- API 응답시간 300ms, QPS 50, maxPoolSize=10
- TPS = (1000ms / 300ms) × 10 = 약 33
- QPS 50 → 17개 요청 대기
- OSIV true면 JSON 직렬화 시간까지 커넥션 점유 → 실제 TPS는 33보다 더 낮아짐
- connectionTimeout 초과 → 503 에러 발생

---

## 6. 언제 사용하면 안되는가

| 상황                      | 이유                                         |
|-------------------------|--------------------------------------------|
| OSIV true + 고트래픽 환경     | 커넥션 점유 시간 증가 → 풀 고갈                        |
| 대용량 배치 처리               | 영속성 컨텍스트에 객체 계속 누적 → OOM                   |
| 단순 조회 API에 Entity 직접 반환 | Dirty Checking 불필요한 스냅샷 생성 → DTO 프로젝션이 효율적 |
