# 2026-04-21 | JPA N+1 문제 원인 + 해결

## 오늘 학습 한 줄 요약

N+1은 쿼리 1번으로 끝날 걸 N+1번 날리는 문제.
LAZY든 EAGER든 발생 가능하고, fetch join / @EntityGraph / BatchSize로 해결한다.

---

## 핵심 개념 정리

### N+1이란

쿼리 1번으로 끝날 걸 N+1번 날리는 문제.

```
이벤트 10개 조회 → 1번
각 이벤트마다 회차 따로 조회 → 10번
총 11번 = 1 + N
```

### LAZY vs EAGER — N+1과의 관계

흔한 오해: "LAZY로 설정하면 N+1이 안 생긴다" → **틀렸음**

|              | EAGER | LAZY           |
|--------------|-------|----------------|
| 연관 데이터 로딩 시점 | 즉시    | 접근할 때          |
| N+1 발생 가능?   | 가능    | 가능 (루프에서 접근 시) |
| 실무 기본값       | ❌     | ✅              |

LAZY는 N+1을 "방지"하는 게 아니라 "지연"시키는 것.
루프에서 연관 데이터에 접근하는 순간 쿼리가 N번 터진다.

```java
List<ShowtimeSeat> seats = showtimeSeatRepository.findAll(); // 1번

for (ShowtimeSeat s : seats) {
    s.getSeat().getSeatNumber();      // 여기서 N번
    s.getShowtime().getShowAt();      // 여기서 N번
}
// 총 1 + N + N번
```

### 해결 방법 3가지

#### 1. fetch join

JPQL로 연관 데이터를 JOIN해서 한 번에 가져오는 방법.

```java
@Query("SELECT ss FROM ShowtimeSeat ss JOIN FETCH ss.seat WHERE ss.showtime.id = :id")
List<ShowtimeSeat> findWithSeat(@Param("id") Long id);
```

실제 나가는 SQL:

```sql
SELECT ss.*, s.*
FROM showtime_seat ss
INNER JOIN seat s ON ss.seat_id = s.id
WHERE ss.showtime_id = ?
-- 1번으로 끝
```

#### 2. @EntityGraph

어노테이션으로 연관 데이터를 한 번에 가져오는 방법.
fetch join과 결과는 동일, 작성이 더 간단함.

```java
@EntityGraph(attributePaths = {"seat"})
List<ShowtimeSeat> findByShowtimeId(Long showtimeId);
```

#### 3. BatchSize

N번 나가는 쿼리를 IN절로 묶어서 1번으로 줄이는 방법.

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "showtime", fetch = FetchType.LAZY)
private List<ShowtimeSeat> showtimeSeats;
```

```sql
-- 100번 → 1번으로 묶임
SELECT * FROM seat WHERE id IN (1, 2, 3, ... 100);
```

### 언제 무엇을 선택하는가

| 상황              | 선택           |
|-----------------|--------------|
| 복잡한 조건 + 연관 데이터 | fetch join   |
| 단순 조회, 연관 1~2개  | @EntityGraph |
| 페이징 + 연관 데이터    | BatchSize    |

#### ⚠️ fetch join + 페이징은 위험

fetch join과 페이징을 같이 쓰면 JPA가 전체 데이터를 메모리에 올린 뒤 페이징 처리함.
데이터가 많으면 OOM 발생 가능. 이때 BatchSize가 대안.

## 현재 프로젝트 연결 (TASK-011, TASK-017)

### `/events` 조회

문제가 될 수 있었던 흐름:

```
이벤트 10개 조회 → 1번
각 이벤트마다 min(showAt) 따로 조회 → 10번
총 11번
```

실제 구현:

- 전용 JOIN 쿼리로 `min(showAt)`을 한 번에 처리 → N+1 없음

### `/showtimes/{showtimeId}/seats` 조회

문제가 될 수 있었던 흐름:

```
showtime_seat 조회 1번
각 seat마다 seat 조회 100번
각 seat마다 seat_grade_price 조회 100번
총 201번
```

실제 구현:

- `showtime_seat`, `seat`, `seat_grade_price` 3개 테이블 JOIN 한 번에 처리 → 1번으로 끝

### 장애 포인트

티켓팅 오픈 순간 동시 사용자 1,000명이 좌석 조회한다고 가정하면:

```
JOIN 없을 때: 201번 × 1,000명 = 201,000번 쿼리 → DB 순간 폭발
JOIN 있을 때: 1번 × 1,000명 = 1,000번 쿼리 → 정상
```

## Q&A

### Q1. N+1 문제가 무엇인가요?

쿼리 1번으로 끝날 걸 N+1번 날리는 문제입니다.
예를 들어 ShowtimeSeat 100개를 조회한 뒤 루프에서 각 seat에 접근하면,
`SELECT * FROM seat WHERE id = ?`가 100번 추가로 나가서 총 101번이 됩니다.
데이터가 늘수록 쿼리 수가 선형으로 증가해 DB 부하가 급증합니다.

---

### Q2. LAZY 로딩인데 왜 N+1이 발생하나요?

LAZY는 N+1을 방지하는 게 아니라 로딩을 지연시키는 설정입니다.
처음 조회 시에는 연관 데이터를 가져오지 않지만,
이후 루프에서 연관 데이터에 접근하는 순간 그때마다 쿼리가 나갑니다.
즉, LAZY든 EAGER든 N+1은 발생할 수 있고, 해결은 fetch join이나 @EntityGraph로 해야 합니다.

---

### Q3. fetch join과 @EntityGraph의 차이는 무엇이고 언제 각각 선택하나요?

둘 다 연관 데이터를 JOIN으로 한 번에 가져오는 방법이고 결과는 동일합니다.
차이는 작성 방식입니다.

fetch join은 JPQL로 직접 쿼리를 작성하기 때문에 복잡한 조건이 있을 때 유리합니다.
@EntityGraph는 어노테이션으로 간단하게 표현할 수 있어서 단순 조회에서 더 편리합니다.

현재 프로젝트 좌석 조회처럼 3개 테이블을 JOIN하고 정렬 조건까지 있는 경우는 fetch join이 적합하고,
단순히 연관 엔티티 1~2개만 가져오는 경우는 @EntityGraph로 충분합니다.

---

### Q4. (Cross) N+1 문제가 커넥션 풀에는 어떤 영향을 주나요?

N+1이 발생하면 쿼리 수가 N배로 늘어나고, 각 쿼리는 커넥션을 점유합니다.
트랜잭션 안에서 N+1이 발생하면 커넥션 점유 시간이 길어지고,
동시 요청이 많으면 커넥션 풀이 고갈될 수 있습니다.

예를 들어 maxPoolSize=10, 트랜잭션 내 N+1로 쿼리가 201번 나가는 상황에서
QPS가 높으면 커넥션 대기 → connectionTimeout → 503 에러 흐름으로 이어집니다.

"N+1 → 트랜잭션 길어짐 → 커넥션 점유 → 풀 고갈"이 연결되는 핵심 장애 흐름입니다.

---

### Q5. (숫자) 좌석 100개 조회 시 N+1이 발생하면 쿼리가 몇 번 나가고, 동시 사용자 1,000명이면 총 몇 번인가요?

현재 프로젝트 기준으로 ShowtimeSeat가 Seat와 SeatGradePrice를 각각 LAZY로 참조하고 있습니다.

```
showtime_seat 조회  1번
seat 조회          100번
seat_grade_price   100번
총                 201번
```

동시 사용자 1,000명이면 201 × 1,000 = 201,000번입니다.
JOIN 쿼리 1번으로 처리하면 1,000번으로 줄어듭니다.
약 200배 차이이고, 티켓팅 오픈처럼 트래픽이 순간 폭증하는 상황에서 DB가 그대로 폭발하는 원인이 됩니다.
