# Week 5 | 2026-04-16 HikariCP + 트랜잭션 길이 → 커넥션 풀 고갈

---

## 오늘 학습 요약

트랜잭션은 커넥션을 점유하므로, 트랜잭션이 길어질수록 커넥션 풀 고갈로 이어진다.
외부 I/O 분리와 `readOnly = true` 활용이 핵심 해결책이다.

---

## 1. HikariCP 내부 동작

### 커넥션 획득 흐름

```
요청 들어옴
  → HikariCP에서 idle 커넥션 탐색
  → 있으면 → 즉시 반환
  → 없으면 → 새 커넥션 생성 시도 (maxPoolSize까지)
  → maxPoolSize 초과 → 대기 (connectionTimeout까지)
  → timeout 초과 → SQLTransientConnectionException 발생
```

### 핵심 설정값

| 설정                  | 기본값 | 의미             |
|---------------------|-----|----------------|
| `maxPoolSize`       | 10  | 최대 커넥션 수       |
| `connectionTimeout` | 30초 | 커넥션 대기 최대 시간   |
| `idleTimeout`       | 10분 | idle 커넥션 유지 시간 |

### 장애 로그

```
Connection is not available, request timed out after 30000ms
```

## 2. 트랜잭션 길이 → 커넥션 풀 고갈

### 처리량 공식

```
TPS = (1000ms / 트랜잭션 평균 시간ms) × maxPoolSize
```

예시:

- 트랜잭션 평균 500ms, maxPoolSize 10
- TPS = (1000 / 500) × 10 = **20**
- QPS 100 유입 시 → 80개 대기 → connectionTimeout 초과 → 503

### 트랜잭션이 길어지는 주요 원인

```java

@Transactional
public void reserve(ReservationRequest request) {
  reservationRepository.save(...);       // DB 작업

  paymentClient.pay(...);                // ❌ 외부 API (1~3초)
  //    커넥션 점유 시간 폭증

  paymentRepository.save(...);           // DB 작업
}
```

### 해결 전략

```java
// ✅ 외부 API를 트랜잭션 밖으로 분리
public void reserve(ReservationRequest request) {
  PaymentResult result = paymentClient.pay(...);  // 트랜잭션 밖
  saveReservation(request, result);               // 트랜잭션 안
}

@Transactional
private void saveReservation(...) {
  reservationRepository.save(...);
  paymentRepository.save(...);
}
```

## 3. readOnly = true 정확한 이해

### 하는 일

```
readOnly = true
  → dirty checking 스냅샷 생성 생략 → 메모리 절약
  → DB 드라이버/ORM에 읽기 전용 힌트 전달
  → 락 여부에는 관여하지 않음
```

### 락 여부는 무엇이 결정하나

```
락 여부 = 어떤 SQL이냐 + 격리수준
  → 일반 SELECT           → MVCC 스냅샷 읽기 → 락 없음
  → SELECT FOR UPDATE     → 배타락(X) 획득
  → UPDATE                → Row Lock 획득
```

`readOnly = true`는 위 동작에 영향을 주지 않는다.

### 좋은 패턴

```java

@Transactional(readOnly = true)  // 클래스 기본 - 읽기는 readOnly
public class PaymentService {

  @Transactional               // 쓰기만 별도 선언
  public PaymentResponse pay(...) { ...}
}
```

## 4. REQUIRES_NEW와 커넥션 풀

```
트랜잭션 A 실행 중 → 커넥션 1개 점유
  → REQUIRES_NEW 호출 → 새 커넥션 1개 추가 점유
  → 동시에 커넥션 2개 사용

maxPoolSize=10 → 사실상 동시 처리 5개로 반감
```

→ REQUIRES_NEW 남용은 커넥션 풀을 빠르게 소진시킨다.

## 5. 현재 프로젝트 연결 (TASK-035, TASK-036)

### ✅ 잘 설계된 부분

**Mock 결제라 외부 API가 트랜잭션 안에 없다.**

```java
// PaymentService 주석
// 실운영 시 PG 콜백 기반 비동기 처리로 전환 필요
```

**`readOnly = true` + 메서드별 `@Transactional` 조합 사용 중.**

**`processPayment()` 트랜잭션이 짧다.**

- Reservation 조회 1회
- Payment 저장 1회
- 상태 변경 (dirty checking, in-memory 연산)
- Redis 저장 1회 (sub-millisecond, 영향 미미)

### ⚠️ 면접에서 짚힐 수 있는 부분

`pay()` 트랜잭션 안에 Redis I/O가 있다.

```java

@Transactional
public PaymentResponse pay(...) {
  return idempotencyRedisRepository.find(idempotencyKey)  // ← Redis I/O
    .orElseGet(() -> processPayment(...));
}
```

Redis는 in-memory DB 특성상 응답시간이 매우 짧아 (Redis 공식 문서 기준 sub-millisecond) 현실적 위험도는
낮다.
단, 수 초가 걸리는 PG API와는 다르게 판단하는 이유를 설명할 수 있어야 한다.

> 판단 기준: "트랜잭션 길이를 의미 있게 늘리느냐"

### 실 PG 전환 시 면접 답변

> "현재는 Mock 결제라 외부 API 호출이 트랜잭션 밖에 없습니다.
> 실 PG 연동 시에는 PG 호출을 트랜잭션 밖으로 분리하고,
> 콜백 수신 후 DB 상태를 업데이트하는 구조로 전환할 계획입니다.
> 트랜잭션 안에 외부 API 호출이 들어가면 커넥션 점유 시간이 길어져
> 커넥션 풀 고갈로 이어지기 때문입니다."

## 6. in-memory 연산이란

```java
savedPayment.success();           // Java 객체 필드값만 변경 (DB 쿼리 없음)
reservation.

confirm();            // Java 객체 필드값만 변경
reservation.

getHold().

confirm();  // Java 객체 필드값만 변경
          ↓
트랜잭션 커밋
시점
  →

```

DB I/O 없이 메모리에서만 일어나는 작업 = in-memory 연산.

## 7.Q&A

---

**Q1.** HikariCP에서 커넥션을 못 가져오면 어떤 예외가 발생하나요?

**A1.**
`SQLTransientConnectionException`이 발생합니다.
HikariCP는 커넥션을 요청했을 때 `connectionTimeout` 내에 가져오지 못하면
이 예외를 던지고, 로그에는 아래 메시지가 찍힙니다.

```
Connection is not available, request timed out after 30000ms
```

기본 `connectionTimeout`은 30초이며, 이 시간을 초과하면 요청이 실패합니다.

---

**Q2.** 트랜잭션 평균 처리 시간이 200ms이고 maxPoolSize가 10이면 초당 최대 처리량(TPS)은 얼마인가요?

**A2.**

```
TPS = (1000ms / 200ms) × 10 = 50 TPS
```

초당 50개 요청을 처리할 수 있습니다.
QPS 100이 유입되면 50개는 대기 상태가 되고,
`connectionTimeout` 내에 처리되지 못한 요청은 예외가 발생해 503 에러로 이어집니다.
트랜잭션 시간이 짧을수록 커넥션 반납이 빨라져 처리량이 올라갑니다.

---

**Q3.** 외부 결제 API 호출을 `@Transactional` 안에 넣으면 왜 위험한가요?

**A3.**
`@Transactional`은 시작 시점에 커넥션을 획득하고 커밋/롤백 전까지 점유합니다.
외부 결제 API 호출이 트랜잭션 안에 있으면, API 응답을 기다리는 동안 커넥션이 계속 점유됩니다.

예를 들어 PG API 응답시간이 2초라면,
트랜잭션 하나가 커넥션을 2초간 점유하게 되어
maxPoolSize=10 기준 TPS가 5로 급감합니다.
트래픽이 몰리면 커넥션 풀이 고갈되고 503 에러가 대량 발생합니다.

해결책은 외부 API 호출을 트랜잭션 밖으로 분리하고,
결과값만 가지고 트랜잭션에 진입하는 구조입니다.

---

**Q4.** [Cross] `REQUIRES_NEW` 전파 레벨을 남용하면 커넥션 풀에 어떤 영향을 주나요?

**A4.**
`REQUIRES_NEW`는 기존 트랜잭션을 일시 중단하고 새 트랜잭션을 시작합니다.
이때 새 커넥션을 별도로 획득하므로, 하나의 요청에서 커넥션 2개를 동시에 점유하게 됩니다.

```
트랜잭션 A → 커넥션 1 점유
  → REQUIRES_NEW 호출 → 커넥션 2 추가 점유
  → 두 커넥션 동시 사용 중
```

maxPoolSize=10이면 사실상 동시 처리 가능한 요청이 5개로 반감됩니다.
호출 depth가 깊어질수록 커넥션 소비가 배로 늘어
커넥션 풀 고갈과 데드락 위험도 함께 올라갑니다.

---

**Q5.** [숫자] QPS 200 유입 상황에서 TPS가 50밖에 안 나온다면 커넥션 풀과 트랜잭션 관점에서 원인을 어떻게 분석하시겠어요?

**A5.**
우선 TPS 공식으로 역산합니다.

```
50 TPS = (1000ms / 트랜잭션 시간) × maxPoolSize
```

예를 들어 maxPoolSize=10이라면 트랜잭션 평균 시간이 200ms라는 뜻입니다.
QPS 200 대비 TPS 50이면 150개 요청이 대기 중인 상황입니다.

확인 순서는 아래와 같습니다.

1. HikariCP active connections = maxPoolSize 상태 지속 여부 확인
2. slow query log에서 오래 걸리는 쿼리 확인
3. 트랜잭션 안에 외부 I/O(HTTP 호출, 파일 I/O 등)가 있는지 확인
4. `REQUIRES_NEW` 남용 여부 확인

원인에 따라 해결 방향이 달라집니다.
슬로우 쿼리가 원인이면 인덱스 튜닝,
외부 I/O가 원인이면 트랜잭션 밖으로 분리,
maxPoolSize가 너무 작으면 적절히 증가시키되
트랜잭션 범위 최소화를 먼저 검토합니다.

> readOnly 활용이 핵심 해결책입니다."
