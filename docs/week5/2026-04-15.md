# Week 5 | 2026-04-15 — 트랜잭션 전파 레벨 (Propagation)

## 한 줄 요약

중첩 트랜잭션 경계를 명시적으로 제어하는 방법

---

## 왜 필요한가?

서비스 A가 서비스 B를 호출할 때, B의 트랜잭션을 어떻게 처리할지 기준이 없으면 개발자 의도와 다르게 동작한다.

```
serviceA() → 트랜잭션 진행 중
    └─ serviceB() → 합류? 새로 만들기? 부분 롤백?
```

---

## 핵심 전파 레벨 3가지

| 전파 레벨            | 동작                       | 커넥션   | 사용 시점         |
|------------------|--------------------------|-------|---------------|
| `REQUIRED` (기본값) | 기존 트랜잭션 합류, 없으면 새로 생성    | 1개 공유 | 대부분의 경우       |
| `REQUIRES_NEW`   | 기존 트랜잭션 일시 중단, 항상 새 트랜잭션 | 2개 점유 | 독립 커밋이 필요할 때  |
| `NESTED`         | SavePoint 생성, 부분 롤백 가능   | 1개 공유 | 부가 기능 실패 허용 시 |

---

## REQUIRED

```java

@Transactional
public void confirmReservation() {
  reservation.confirm();
  seatService.hold(); // REQUIRED → 같은 트랜잭션 합류
}
```

- 기존 트랜잭션 있음 → 합류 (커넥션 공유)
- 기존 트랜잭션 없음 → 새로 생성
- B 예외 발생 → **A, B 전체 롤백**

### 프로젝트 연결 (TASK-012, TASK-014)

좌석 선점 시 1, 2, 3번 중 1번 실패 → 전체 롤백이 맞음.  
부분 성공은 사용자 의도와 다르기 때문.

---

## REQUIRES_NEW

```java

@Transactional
public void confirmReservation() {
  reservation.confirm();
  paymentService.pay(); // REQUIRES_NEW → 독립 트랜잭션
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void pay() {
  paymentRepository.save(paymentLog); // 예약 롤백돼도 반드시 남아야 함
}
```

```
A 트랜잭션 시작 (커넥션 1)
    └─ B 호출 → A 일시 중단
         → B 별도 트랜잭션 시작 (커넥션 2)
         → B 커밋 완료
    └─ A 재개
A 실패 → A만 롤백, B는 이미 커밋됨
```

### ❗ 주의 — 커넥션 2개 동시 점유

```
maxPoolSize = 10
REQUIRES_NEW 남발 시 → 요청 1개당 커넥션 2개
→ 실질적으로 5개 요청만 처리 가능
→ 커넥션 풀 고갈 → 대기 → timeout → 503
```

### 프로젝트 연결 (TASK-035, TASK-036)

PG사 결제 후 예약이 롤백돼도 결제 기록은 반드시 남아야 함.  
기록 없으면 환불 근거 없음 → 사용자 돈 증발 장애.

---

## NESTED

```java

@Transactional
public void confirmReservation() {
  reservation.confirm();
  notificationService.send(); // NESTED → SavePoint
}

@Transactional(propagation = Propagation.NESTED)
public void send() {
  // 알림 실패 → SavePoint 복귀 (예약은 살아있음)
  notification.send();
}
```

```
A 트랜잭션 시작
    └─ SavePoint 생성
         └─ B 실행
              → B 실패 → SavePoint로 복귀 (A 유지)
              → B 성공 → A 커밋 시 같이 커밋
```

### REQUIRES_NEW vs NESTED 비교

|           | REQUIRES_NEW | NESTED              |
|-----------|--------------|---------------------|
| 커넥션       | 2개           | 1개                  |
| B 실패 시    | A 영향 없음      | A 유지 (SavePoint 복귀) |
| B 성공 후 커밋 | 즉시 독립 커밋     | A 커밋 시 같이 커밋        |
| 사용 목적     | 반드시 독립 기록    | 부가 기능 부분 실패 허용      |

### 프로젝트 연결

알림 발송 실패가 예약 확정에 영향을 주면 안 되는 경우.  
부가 기능 실패는 허용, 본 기능은 유지.

---

## 장애 흐름 (면접 필수)

```
REQUIRES_NEW 남발
→ 요청당 커넥션 2개 점유
→ maxPoolSize=10 → 실질 5개 요청만 처리
→ 커넥션 풀 고갈
→ Connection is not available, request timed out
→ 503 에러
```

---

## 한 줄 요약

> "REQUIRED는 기존 트랜잭션에 합류하고, REQUIRES_NEW는 독립 트랜잭션을 생성하며 커넥션을 2개 점유하므로 남발 시 커넥션 풀
> 고갈 위험이 있습니다. NESTED는 SavePoint로 부분 롤백을 허용하되 커넥션은 1개만 사용합니다."

## Q&A

**Q1. REQUIRED와 REQUIRES_NEW의 차이는?**  
REQUIRED는 기존 트랜잭션이 있으면 합류하고 없으면 새로 생성해요. REQUIRES_NEW는 항상 새 트랜잭션을 만들고 기존 트랜잭션은
일시 중단돼요. 커넥션도 별도로 생성되어 독립적으로 커밋/롤백돼요.

**Q2. REQUIRES_NEW를 남발하면?**  
요청 1개당 커넥션이 2개 점유돼요. maxPoolSize=10이면 실질적으로 5개 요청만 처리 가능하고 커넥션 풀 고갈 → 대기 →
timeout → 503 에러가 발생해요.

**Q3. 결제 기록에 REQUIRES_NEW를 쓰는 이유는?**  
PG사와 연동되는 순간 실제로 돈이 빠져나가요. 예약이 롤백돼도 결제 기록은 반드시 남아야 환불 처리가 가능해요. 기록이 없으면 환불 근거가
없어서 사용자 돈이 증발하는 장애가 발생해요.

**Q4. (Cross) REQUIRES_NEW가 커넥션 풀에 미치는 영향은?**  
기존 트랜잭션 커넥션 1개 + REQUIRES_NEW 커넥션 1개 → 동시에 2개 점유 → 풀 크기 절반만 유효하게 동작 → 트래픽 증가 시
커넥션 풀 고갈 위험.
