- JDK Proxy vs CGLIB 차이 이해

## 1. JDK Proxy vs CGLIB

| 항목             | JDK Proxy | CGLIB         |
|----------------|-----------|---------------|
| 기반             | 인터페이스     | 클래스 상속        |
| 조건             | 인터페이스 필수  | 인터페이스 불필요     |
| final 메서드      | 상관없음      | 적용 불가         |
| Spring Boot 기본 | ❌         | ✅ (2.x부터 기본값) |

### JDK Proxy

```java
// 인터페이스가 있을 때
public interface OrderService { ...
}

public class OrderServiceImpl implements OrderService { ...
}
// → 인터페이스 기반 프록시 생성
```

### CGLIB

```java
// 인터페이스 없을 때
public class OrderService { ...
}
// → 클래스를 상속한 프록시 생성
```

> **Spring Boot 2.x부터 인터페이스 유무와 관계없이 CGLIB이 기본값**

## 2. @Transactional 롤백 안 되는 케이스 3가지

### Case 1 — self-invocation

**문제**

```java

@Service
public class AService {

  public void createOrder() {
    this.processPayment(); // ❌ this = 원본 객체 직접 호출 → 프록시 우회
  }

  @Transactional
  public void processPayment() { ...}
}
```

**원인**

```
외부에서 호출   → 프록시 경유 → ✅ 트랜잭션 적용
this로 내부 호출 → 프록시 우회 → ❌ 트랜잭션 미적용
```

**해결 — 별도 Bean으로 분리**

```java

@Service
public class OrderService {
  private final PaymentService paymentService; // 주입받은 것 = 프록시 객체

  public void createOrder() {
    paymentService.processPayment(); // ✅ 프록시 경유
  }
}

@Service
public class PaymentService {
  @Transactional
  public void processPayment() { ...}
}
```

---

### Case 2 — checked exception은 기본 롤백 대상 아님

**문제**

```java

@Transactional
public void processPayment() throws IOException {
  saveOrder();
  throw new IOException(); // ❌ checked → 롤백 안 됨
}
```

| 예외 종류                        | 기본 롤백 여부 |
|------------------------------|----------|
| RuntimeException (unchecked) | ✅ 롤백     |
| Error                        | ✅ 롤백     |
| Exception (checked)          | ❌ 롤백 안 됨 |

**해결 — rollbackFor 명시**

```java

@Transactional(rollbackFor = Exception.class) // ✅
public void processPayment() throws IOException {
  saveOrder();
  throw new IOException(); // 이제 롤백됨
}
```

> 롤백과 예외 전파는 별개 — 롤백 후 IOException은 호출자에게 그대로 전파됨

---

### Case 3 — private 메서드는 @Transactional 적용 안 됨

**문제**

```java

@Transactional
private void processPayment() { ...} // ❌ private → CGLIB 오버라이드 불가
```

**원인**
CGLIB은 클래스를 **상속**해서 메서드를 오버라이드하는 방식인데,
`private`은 오버라이드 자체가 불가능함

**해결 — public으로 변경**

## 3. 프로젝트 연결 (TASK-035, TASK-036)

| 케이스               | 티켓팅 프로젝트 장애 시나리오                                           |
|-------------------|------------------------------------------------------------|
| self-invocation   | 결제 + 예약 저장이 같은 클래스 안에서 this 호출 시 → 롤백 누락 → 결제는 됐는데 좌석 안 잡힘 |
| checked exception | 외부 Mock 결제 API IOException 발생 시 rollbackFor 없으면 롤백 누락      |
| REQUIRES_NEW 남발   | 커넥션 2개 점유 → maxPoolSize=10 → 실질 TPS 절반 → 503 에러            |

---

## 4. 핵심 연결 흐름

```
self-invocation
→ 트랜잭션 없음
→ 롤백 누락
→ 데이터 정합성 오염

해결 시 REQUIRES_NEW 사용
→ 커넥션 2개 점유
→ maxPoolSize=10 → 동시 처리 5개
→ 커넥션 풀 고갈 → 503 에러
```

---

## 5. 숫자 기반 운영 감각

```
maxPoolSize = 10
REQUIRES_NEW 사용 시 요청 1개당 커넥션 2개 점유

→ 동시 처리 가능 요청 = 10 / 2 = 5개
→ 6번째 요청부터 대기
→ connectionTimeout 초과 → 503 에러
```

## Q&A

## Q1. JDK Proxy와 CGLIB의 차이는 무엇인가요?

**답변**
JDK Proxy는 인터페이스 기반으로 프록시를 생성하고,
CGLIB은 클래스를 상속해서 프록시를 생성합니다.
Spring Boot 2.x부터는 인터페이스 유무와 관계없이 CGLIB이 기본값입니다.
단, CGLIB은 final 클래스나 final 메서드에는 적용이 불가능합니다.

---

## Q2. self-invocation이 왜 트랜잭션이 적용 안 되나요?

**답변**
@Transactional은 AOP 프록시 기반으로 동작합니다.
외부에서 호출 시 프록시를 경유해서 트랜잭션이 시작되지만,
같은 클래스 안에서 this.메서드()로 호출하면 프록시를 우회하고 원본 객체를 직접 호출합니다.
프록시를 거치지 않으니 트랜잭션이 적용되지 않습니다.
해결책은 별도 Bean으로 분리해서 프록시를 경유하도록 만드는 것입니다.

---

## Q3. checked exception 발생 시 롤백이 안 됐어요. 원인과 해결 방법은?

**답변**
@Transactional의 기본 롤백 대상은 RuntimeException(unchecked)과 Error만입니다.
IOException, SQLException 같은 checked exception은 기본적으로 롤백 대상이 아닙니다.
해결책은 `@Transactional(rollbackFor = Exception.class)`로 명시하는 것입니다.
롤백과 예외 전파는 별개로, 롤백 후 예외는 호출자에게 그대로 전파됩니다.

---

## Q4. (Cross) self-invocation 문제가 커넥션 풀에도 영향을 줄 수 있나요?

**답변**
self-invocation 자체는 트랜잭션이 없어 커넥션을 획득하지 않으므로 커넥션 풀에 직접적인 영향은 없습니다.
하지만 진짜 문제는 롤백 누락으로 인한 데이터 정합성 오염입니다.
예를 들어 결제는 됐는데 예약 저장은 롤백이 안 되는 상황이 생깁니다.
또한 self-invocation 해결을 위해 별도 Bean 분리 + REQUIRES_NEW를 사용하면
커넥션을 2개 점유하게 되어 커넥션 풀 고갈 위험이 생깁니다.

---

## Q5. (숫자) REQUIRES_NEW를 남발하면 maxPoolSize=10 환경에서 어떤 문제가 생기나요?

**답변**
REQUIRES_NEW는 기존 트랜잭션과 별도로 새 트랜잭션을 시작하기 때문에
커넥션을 2개 동시에 점유합니다.

계산하면:

- maxPoolSize = 10
- 요청 1개당 커넥션 2개 점유
- 동시 처리 가능 요청 = 10 / 2 = 5개
- 6번째 요청부터 커넥션 대기
- connectionTimeout 초과 → 503 에러 발생

따라서 REQUIRES_NEW는 꼭 필요한 경우에만 사용하고,
트랜잭션 범위 설계 시 커넥션 점유 수를 반드시 고려해야 합니다.
