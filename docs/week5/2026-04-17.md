## 핵심 개념 정리

### @Transactional 내부 흐름

```
Controller
  → AOP 프록시가 가로챔
  → TransactionInterceptor 실행
  → PlatformTransactionManager
  → HikariCP에서 커넥션 획득
  → ThreadLocal에 커넥션 바인딩
  → 실제 Service 메서드 실행
  → 성공 → commit → 커넥션 반납
  → 실패 → rollback → 커넥션 반납
```

**핵심**: 트랜잭션 = 커넥션 점유. 트랜잭션이 길수록 커넥션을 오래 잡고 있음.

---

### @Transactional 3가지 함정

| 함정                | 원인                  | 해결                                 |
|-------------------|---------------------|------------------------------------|
| self-invocation   | `this`로 호출 → 프록시 우회 | Bean 분리                            |
| checked exception | 기본 롤백 대상 아님         | `rollbackFor = Exception.class` 명시 |
| private 메서드       | 프록시 적용 불가           | public으로 변경 또는 Bean 분리             |

#### self-invocation 핵심

```java
// ❌ 문제 — 같은 클래스 내 호출
@Transactional
public void reserve() {
  internalMethod(); // 묵시적 this.internalMethod() → 프록시 우회
}

@Transactional(propagation = REQUIRES_NEW)
public void internalMethod() {
  // @Transactional 적용 안 됨
}
```

```java
// ✅ 해결 — Bean 분리
@Service
public class ReservationService {
  private final ReservationInternalService internalService;

  @Transactional
  public void reserve() {
    internalService.internalMethod(); // 프록시를 통해 호출
  }
}

@Service
public class ReservationInternalService {
  @Transactional(propagation = REQUIRES_NEW)
  public void internalMethod() {
  }
}
```

### 전파 레벨 비교

| 전파 레벨         | 동작                     | 커넥션   | 사용 케이스          |
|---------------|------------------------|-------|-----------------|
| REQUIRED (기본) | 기존 트랜잭션 참여, 없으면 생성     | 1개 공유 | 일반적인 서비스 로직     |
| REQUIRES_NEW  | 항상 새 트랜잭션 생성, 기존 일시 중단 | 2개 점유 | 결제 내역 저장, 감사 로그 |
| NESTED        | 중첩 트랜잭션 (Savepoint)    | 1개 공유 | 부분 롤백 필요 시      |

#### REQUIRES_NEW 사용 기준

**써야 하는 경우**

- 예약 롤백돼도 결제 내역은 남아야 할 때
- 알림 전송 실패해도 예약은 성공이어야 할 때

**쓰면 안 되는 경우**

- 트래픽이 많은 핵심 API 경로 (커넥션 2배 소비)

### 트랜잭션 길이 → 커넥션 풀 고갈 흐름

```
[장애 흐름]
트랜잭션 시작 → 커넥션 획득 → 외부 API 호출 (트랜잭션 안)
→ 커넥션 점유 시간 증가 → 커넥션 풀 소진
→ 다른 요청 대기 → connectionTimeout 초과
→ "Connection is not available, request timed out"
→ 503 에러
```

#### TPS 계산

```
REQUIRED
maxPoolSize=10, 트랜잭션 200ms
→ TPS = (1000 / 200) × 10 = 50 TPS

REQUIRES_NEW (커넥션 2배 소비)
maxPoolSize=10, 트랜잭션 200ms
→ 동시 처리 가능 요청 = 10 / 2 = 5개
→ TPS = (1000 / 200) × 5 = 25 TPS
→ 요청 200개 유입 시 175개 대기 → 풀 고갈 더 빠르게 발생
```

## 면접 한 줄 요약 모음

| 개념                | 면접 한 줄 요약                                        |
|-------------------|--------------------------------------------------|
| @Transactional 동작 | AOP 프록시가 커넥션 획득 / commit / rollback을 앞뒤로 감싸서 처리  |
| self-invocation   | `this` 참조로 프록시를 우회하기 때문에 @Transactional이 적용되지 않음 |
| checked exception | 기본 롤백 대상이 아니므로 rollbackFor로 명시 필요                |
| REQUIRES_NEW      | 커넥션을 2개 점유하므로 트래픽 많은 경로에서 풀 고갈 위험                |
| 커넥션 풀 고갈          | 긴 트랜잭션 + 외부 API 호출이 원인 → 트랜잭션 분리로 해결             |
