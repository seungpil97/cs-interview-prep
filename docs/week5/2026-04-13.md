## 1. 한 줄 요약

> `@Transactional`은 AOP 프록시 기반으로 동작하며, 트랜잭션 시작/종료를 원본 메서드 앞뒤에 자동으로 붙여준다.

---

## 2. 왜 필요한가 (Why)

트랜잭션 처리를 직접 짜면 모든 서비스 메서드마다 아래 코드가 반복된다.

```java
Connection conn = dataSource.getConnection();
conn.setAutoCommit(false);
try {
    seatRepository.hold(seatId);
    reservationRepository.save(userId, seatId);
    conn.commit();
} catch (Exception e) {
    conn.rollback();
} finally {
    conn.close();
}
```

이를 **횡단 관심사(Cross-cutting concern)** 라고 한다.  
`@Transactional` + AOP는 이 반복 코드를 분리하기 위해 등장했다.

---

## 3. 내부 동작 흐름

```
Controller
    ↓
ReservationService$$SpringCGLIB  ← 프록시 객체 (Spring이 런타임에 생성)
    ↓
트랜잭션 시작
    ↓
커넥션 획득 (HikariCP)
    ↓
ThreadLocal에 커넥션 바인딩      ← 같은 스레드 안에서 커넥션 공유
    ↓
원본 ReservationService.reserve() 실행
    ↓
성공 → 커밋 / 실패 → 롤백
    ↓
ThreadLocal에서 커넥션 제거
    ↓
커넥션 반납 (HikariCP로 돌아감)
```

---

## 4. 핵심 개념 3가지

### 4-1. 프록시 객체

Spring은 `@Transactional`이 붙은 Bean을 **원본 그대로 등록하지 않는다.**  
원본을 감싼 **프록시 객체**를 만들어서 등록한다.

```java
// 내가 만든 원본
public class ReservationService { ... }

// Spring이 실제로 등록하는 것
public class ReservationService$$SpringCGLIB extends ReservationService {
    public void reserve(Long seatId, Long userId) {
        // 트랜잭션 시작
        원본.reserve(seatId, userId);
        // 트랜잭션 종료 (커밋 or 롤백)
    }
}
```

> `@Autowired`로 주입받는 건 원본이 아니라 프록시다.

---

### 4-2. ThreadLocal

**스레드마다 고유한 저장공간.**  
같은 트랜잭션 안에서 `seatRepository`, `reservationRepository`가 **같은 커넥션**을 쓰기 위해 필요하다.

```
트랜잭션 시작 → 커넥션 획득 → ThreadLocal 저장
    ↓
seatRepository        → ThreadLocal에서 꺼내서 사용
reservationRepository → ThreadLocal에서 꺼내서 사용 (같은 커넥션)
    ↓
트랜잭션 종료 → ThreadLocal 제거 → 커넥션 반납
```

ThreadLocal이 없으면 → 두 Repository가 다른 커넥션을 쓰게 되고 → 같은 트랜잭션으로 묶이지 않는다.

---

### 4-3. 커넥션 점유 = 트랜잭션 길이

트랜잭션이 시작되면 **커넥션을 점유**하고, 종료될 때만 반납한다.

```
트랜잭션 내 외부 API 호출 포함
    ↓
외부 API 응답 3초 대기
    ↓
3초 동안 커넥션 계속 점유
    ↓
다른 요청들은 커넥션 못 받고 대기
    ↓
connectionTimeout 초과 → 503 에러
```

---

## 5. 사용하면 안 되는 경우 ❗

| 상황 | 이유 |
|------|------|
| 외부 API 호출을 트랜잭션 안에 포함 | 응답 지연 → 커넥션 점유 시간 증가 → 커넥션 풀 고갈 |
| `private` 메서드에 붙이기 | 프록시가 override 불가 → 트랜잭션 미적용 |
| 같은 클래스 내부 호출 (self-invocation) | 프록시 우회 → 트랜잭션 미적용 |

## 6. 숫자로 이해하기 (운영 감각)

```
트랜잭션 평균 2초 + maxPoolSize = 10

TPS = (1000ms / 2000ms) × 10 = 5 TPS

QPS 50 유입 시
→ 45개 요청 대기 → connectionTimeout 초과 → 503 에러
```

## 9. 오늘의 면접 질문

## Q1. `@Transactional`은 내부적으로 어떻게 동작하나요?

> 기본 질문 — 개념 정의

**답변**

"`@Transactional`은 AOP 프록시 기반으로 동작합니다.
Spring이 원본 Bean을 감싼 프록시 객체를 런타임에 생성하고,
프록시가 원본 메서드 앞뒤에 트랜잭션 시작과 종료를 자동으로 붙여줍니다.
내부적으로는 HikariCP에서 커넥션을 획득한 뒤 ThreadLocal에 저장해서,
같은 트랜잭션 안의 모든 Repository가 동일한 커넥션을 사용하도록 보장합니다."

**키워드 순서**

```
AOP 프록시 → 트랜잭션 시작/종료 → HikariCP 커넥션 획득 → ThreadLocal 바인딩
```

---

## Q2. 프록시 객체가 뭔가요? Spring은 왜 프록시를 쓰나요?

> 꼬리 질문 — 동작 원리

**답변**

"프록시는 원본 객체를 감싼 대리 객체입니다.
Spring은 `@Transactional`이 붙은 Bean을 원본 그대로 등록하지 않고,
원본을 상속하거나 인터페이스를 구현한 프록시 객체를 만들어서 등록합니다.
그래서 `@Autowired`로 주입받는 건 원본이 아니라 프록시예요.
프록시를 쓰는 이유는 트랜잭션 처리 코드를 비즈니스 로직에서 분리하기 위해서입니다.
직접 짜면 모든 메서드마다 커넥션 획득/커밋/롤백 코드가 반복되는데,
프록시 + AOP로 이 횡단 관심사를 한 곳에서 처리할 수 있습니다."

**키워드 순서**

```
대리 객체 → 원본 감쌈 → 횡단 관심사 분리 → 비즈니스 로직과 분리
```

---

## Q3. 트랜잭션이 길어지면 어떤 장애가 발생하나요?

> 꼬리 질문 — 실무/장애

**답변**

"트랜잭션이 길어지면 커넥션 풀 고갈이 발생합니다.
트랜잭션이 시작되면 커넥션을 점유하고, 종료될 때만 반납합니다.
예를 들어 트랜잭션 안에 외부 API 호출이 포함돼서 평균 2초가 걸린다면,
maxPoolSize가 10일 때 TPS는 5밖에 안 나옵니다.
QPS가 50이면 45개 요청이 대기하다가 connectionTimeout을 초과해서 503 에러가 납니다.
그래서 외부 API 호출은 반드시 `@Transactional` 밖으로 분리해야 합니다."

**키워드 순서**

```
커넥션 점유 → 트랜잭션 길이 → 커넥션 풀 고갈 → 대기 → timeout → 503
```

---

## Q4. (Cross) ThreadLocal이 없으면 어떤 문제가 생기나요?

> Cross Question — 오늘 개념 + 커넥션 풀 연결

**답변**

"ThreadLocal이 없으면 같은 트랜잭션 안에서 Repository마다 다른 커넥션을 쓰게 됩니다.
예를 들어 `seatRepository`와 `reservationRepository`가 각각 다른 커넥션을 쓰면,
둘이 같은 트랜잭션으로 묶이지 않아서 하나가 실패해도 다른 하나가 롤백되지 않습니다.
데이터 정합성이 깨지는 거예요.
ThreadLocal 덕분에 같은 스레드 안에서는 어디서든 동일한 커넥션을 꺼내 쓸 수 있고,
이게 트랜잭션 원자성 보장의 핵심입니다."

**키워드 순서**

```
ThreadLocal 없음 → 커넥션 각각 → 트랜잭션 분리 → 롤백 미적용 → 정합성 깨짐
```

## Q5. (숫자) 트랜잭션 평균 2초, maxPoolSize=10이면 TPS는 얼마인가요?

> 숫자 기반 질문 — 운영 감각

**답변**

"계산식은 TPS = (1000ms / 트랜잭션 시간ms) × maxPoolSize입니다.
트랜잭션 2초, maxPoolSize 10이면 TPS = 0.5 × 10 = 5 TPS입니다.
QPS가 50이면 초당 45개 요청이 커넥션을 못 받고 대기합니다.
connectionTimeout 기본값이 30초인데, 이 안에 커넥션을 못 받으면 예외가 발생하고 503이 납니다.
실서비스에서 트래픽 스파이크가 오면 순식간에 커넥션 풀이 고갈됩니다.
해결책은 트랜잭션 범위를 최소화하거나, 외부 I/O를 트랜잭션 밖으로 분리하는 겁니다."

**계산 공식**

```
TPS = (1000 / 트랜잭션ms) × maxPoolSize
    = (1000 / 2000) × 10
    = 5 TPS
```
