## 오늘 학습 요약

EXPLAIN으로 인덱스 유무에 따른 탐색 방식 차이를 확인하고,  
인덱스가 **성능뿐 아니라 Lock 범위에도 직접적인 영향**을 미친다는 것을  
프로젝트 코드(TASK-016, TASK-017)로 연결했다.

---

## 핵심 개념

### EXPLAIN 주요 컬럼

| 컬럼      | 의미         | 보는 포인트               |
|---------|------------|----------------------|
| `type`  | 탐색 방식      | **가장 중요** — ALL이면 위험 |
| `key`   | 실제 사용된 인덱스 | NULL이면 인덱스 안 탐       |
| `rows`  | 예상 탐색 행 수  | 숫자 클수록 느림            |
| `Extra` | 부가 정보      | Using index = 좋음     |

### type 컬럼 등급

```
ALL   → Full Scan (최악) ← 인덱스 없을 때
range → 인덱스 범위 탐색 (괜찮음)
ref   → 인데스 일치 탐색 (좋음)
const → 단 1건 (최고)
```

## 실제 EXPLAIN 결과 (프로젝트 DB 직접 측정)

### 인덱스 있는 경우

```
id: 1
select_type: SIMPLE
table: showtime_seat
type: ref                                        ← 인덱스 탐색 ✅
key: idx_showtime_seat_showtime_id_status        ← TASK-017 추가 인덱스
rows: 14                                         ← 14건만 읽음
Extra: Using index condition
```

### 인덱스 없는 경우 (status만으로 조회)

```
id: 1
select_type: SIMPLE
table: showtime_seat
type: ALL                                        ← Full Scan ⚠️
key: NULL                                        ← 인덱스 안 탐
rows: 40                                         ← 전체 다 읽음
Extra: Using where
```

## 인덱스 ↔ 락 연결 (핵심)

```
[인덱스 없는 경우 — SELECT ... FOR UPDATE]
WHERE showtime_id = 10

→ Full Scan → 테이블 전체 읽음
→ 읽은 모든 Row에 Lock 획득
→ 사실상 Table Lock 수준
→ 다른 트랜잭션은 전체가 잠길 때까지 대기

[인덱스 있는 경우 — SELECT ... FOR UPDATE]
WHERE showtime_id = 10

→ B-Tree 탐색 → 해당 Row만 읽음
→ 해당 Row에만 Lock 획득
→ Row Level Lock 최소화
→ 다른 좌석 트랜잭션은 영향 없음
```

### 실서비스 규모로 환산

```
공연 100개 × 좌석 500개 = 50,000건 테이블

인덱스 있음 → rows: ~500건만 Lock
인덱스 없음 → rows: 50,000건 전체 Lock
```

---

## 프로젝트 연결 (TASK-016 + TASK-017)

TASK-016에서 비관적 락(`@Lock(PESSIMISTIC_WRITE)`)을 적용했는데
TASK-017 인덱스가 없었다면?

```
좌석 1개 선점 → SELECT ... FOR UPDATE
→ showtime_seat 테이블 전체 Lock
→ 다른 사람이 다른 좌석 선점하려 해도 전부 대기
→ 티켓팅 오픈 순간 → 모든 요청 직렬화 → 503 폭발
```

**결론: TASK-016(비관적 락)이 제대로 동작하려면 TASK-017(인덱스)이 반드시 필요했다.**

---

## 장애 흐름

```
인덱스 없음
→ SELECT ... FOR UPDATE → Full Scan → 50,000건 Lock
→ QPS 50 유입 → 요청 직렬화
→ Lock 대기 증가 → 커넥션 점유 시간 증가
→ 커넥션 풀 고갈 → connectionTimeout 초과
→ 503 에러 발생
```

### 감지 방법

- `EXPLAIN` type = ALL 확인
- `information_schema.innodb_trx` 에서 lock_wait 상태 다수 확인
- slow_query_log 등장
- DB CPU 사용률 급등

### 장애 한 줄 요약

> "인덱스 없는 SELECT FOR UPDATE로 Full Scan 발생 → 불필요한 Row 전체 Lock → 인덱스 추가로 Lock 범위
> 최소화"

## 질문 & 답안

### Q1. EXPLAIN에서 가장 먼저 봐야 할 컬럼은 무엇이고 왜인가요?

**A.**  
`type` 컬럼을 가장 먼저 봅니다.  
`type`은 MySQL이 테이블을 어떤 방식으로 탐색하는지를 나타내는데,  
`ALL`이면 인덱스 없이 전체 행을 스캔한다는 의미입니다.  
데이터가 100만 건인 테이블에서 `ALL`이 나오면  
Full Scan으로 O(N) 탐색이 발생해 응답 시간이 급격히 느려집니다.  
`key`가 NULL이면 인덱스가 사용되지 않은 것이고,  
`rows`로 예상 탐색 행 수를 숫자로 확인할 수 있습니다.

---

### Q2. `type: ALL`과 `type: ref`의 차이를 내부 동작 수준으로 설명하세요.

**A.**  
`type: ALL`은 Full Scan으로 테이블 처음부터 끝까지 모든 Row를 읽고 조건에 맞는 것만 필터링합니다. O(N) 탐색이라
데이터가 늘어날수록 선형으로 느려집니다.  
`type: ref`는 B-Tree 인덱스를 타고 조건에 맞는 위치로 바로 점프해 해당 Row만 읽습니다. O(log N) 탐색이라 데이터가
늘어나도 성능이 크게 떨어지지 않습니다.  
프로젝트에서 `showtime_seat(showtime_id, status)` 인덱스 추가 전에는 `type: ALL`이었고, 추가
후 `type: ref`로 바뀌면서 탐색 행 수가 40건에서 14건으로 줄었습니다.

---

### Q3. 인덱스가 없는 컬럼에 `SELECT ... FOR UPDATE`를 걸면 어떤 문제가 생기나요?

**A.**  
`SELECT ... FOR UPDATE`는 읽은 Row에 배타락(X Lock)을 겁니다.  
인덱스가 없으면 Full Scan이 발생해 테이블 전체 Row를 읽게 되고  
읽은 모든 Row에 Lock이 걸립니다. 사실상 Table Lock 수준이 됩니다.  
프로젝트에서 `showtime_seat` 테이블에 인덱스 없이 비관적 락을 걸면  
좌석 1개 선점 요청이 테이블 전체 50,000건을 잠급니다.  
다른 사람이 다른 좌석을 선점하려 해도 전부 대기 상태가 되고  
티켓팅 오픈 순간 모든 요청이 직렬화되어 503 에러가 발생할 수 있습니다.  
그래서 인덱스 설계는 성능뿐 아니라 Lock 범위 최소화 차원에서도 필수입니다.

---

### Q4 (Cross). 인덱스가 없을 때 Lock과 커넥션 풀은 어떻게 연결되나요?

**A.**  
인덱스 없음 → Full Scan → 테이블 전체 Lock → Lock 대기 증가, 이렇게 연결됩니다.  
Lock 대기가 길어지면 트랜잭션이 커넥션을 점유한 채 오래 기다리게 됩니다.  
트랜잭션 = 커넥션 점유이기 때문에  
Lock 대기 중인 트랜잭션이 쌓이면 커넥션 풀이 빠르게 소진됩니다.  
예를 들어 Lock 대기 2초, maxPoolSize 10이면 TPS는 5밖에 안 나옵니다.  
QPS 50이 들어오면 45개 요청이 connectionTimeout을 초과해 503 에러가 발생합니다.  
결국 인덱스 문제가 커넥션 풀 고갈로 이어지는 장애 흐름입니다.

---

### Q5 (숫자). 공연 100개 × 좌석 500개 = 50,000건 테이블에서, 인덱스 없이 `SELECT ... FOR UPDATE` QPS 50이 들어오면 어떤 일이 벌어지나요?

**A.**  
먼저 계산을 해보면 Lock 대기로 트랜잭션 시간이 500ms라고 가정했을 때  
maxPoolSize 10 기준 TPS = (1000ms / 500ms) × 10 = 20 TPS입니다.  
QPS 50에서 30개 요청은 즉시 처리가 불가능해 커넥션 대기 상태가 됩니다.  
여기에 인덱스 없는 Full Scan으로 50,000건 전체 Lock이 걸리면  
Lock 대기 시간이 더 늘어나 트랜잭션 시간이 2초로 늘어날 수 있고  
이 경우 TPS는 5로 떨어집니다.  
45개 요청이 connectionTimeout(기본 30초)을 초과하고  
로그에 `Connection is not available, request timed out`이 찍히며  
사용자에게는 503 에러가 반환됩니다.  
해결 방법은 인덱스 추가로 Lock 범위를 최소화하고 트랜잭션 시간을 줄이는 것입니다.
