## 파트 1 — 코딩테스트

### 🧩 타겟 넘버 (`TargetNumber`)

#### 문제 요약

n개의 음이 아닌 정수를 적절히 더하거나 빼서 타겟 넘버를 만드는 경우의 수 구하기

#### 풀이 코드

```java
package week4;

public class TargetNumber {
  int count = 0;

  public int solution(int[] numbers, int target) {
    dfs(numbers, target, 0, 0);
    return count;
  }

  void dfs(int[] numbers, int target, int index, int sum) {
    if (index == numbers.length) {
      if (sum == target) {
        count++;
      }
      return;
    }
    dfs(numbers, target, index + 1, sum + numbers[index]);
    dfs(numbers, target, index + 1, sum - numbers[index]);
  }

  public static void main(String[] args) {
    TargetNumber t = new TargetNumber();
    int[] numbers1 = {1, 1, 1, 1, 1};
    System.out.println(t.solution(numbers1, 3)); // 5

    TargetNumber t2 = new TargetNumber();
    int[] numbers2 = {4, 1, 2, 1};
    System.out.println(t2.solution(numbers2, 4)); // 2
  }
}
```

#### 핵심 아이디어

- 매 index마다 +/- 두 가지 분기로 탐색 → DFS
- 종료 조건: `index == numbers.length` (모든 숫자 사용 완료)
- 끝에 도달했을 때 `sum == target` 이면 `count++`

#### DFS 핵심 패턴 3가지

```java
// 1. 종료 조건 (가장 중요!)
if(index ==numbers.length){...return;}

// 2. + 방향 탐색
dfs(...,index +1, sum +numbers[index]);

// 3. - 방향 탐색
dfs(...,index +1, sum -numbers[index]);
```

#### 복잡도 분석

|    | 복잡도        | 이유                |
|----|------------|-------------------|
| 시간 | **O(2^N)** | 매 단계마다 +/- 2개씩 분기 |
| 공간 | **O(N)**   | 재귀 스택 최대 N층까지 쌓임  |

> 💡 **면접 포인트**: 재귀 깊이가 너무 깊어지면 `StackOverflowError` 발생 → 반복문 + 스택 자료구조로 전환

#### 문제 ↔ CS 개념 연결

| 알고리즘   | CS 개념 | 실무 연결                                         |
|--------|-------|-----------------------------------------------|
| DFS 재귀 | 콜스택   | 재귀 깊이 초과 시 StackOverflowError → 반복문 + 스택으로 전환 |

## 파트 2 — CS 개념: DB 인덱스 (B-Tree 구조)

### 📌 핵심 개념 정리

#### 인덱스란?

- DB에서 데이터를 빠르게 찾기 위한 별도의 자료구조
- **책의 목차**와 동일한 개념
- Full Scan O(N) → B-Tree 탐색 O(log N)

#### 인덱스 없을 때 vs 있을 때

```sql
-- 인덱스 없을 때: 100만 건 Full Scan O(N)
SELECT *
FROM users
WHERE email = 'kim@gmail.com';

-- 인덱스 추가
CREATE INDEX idx_email ON users (email);

-- 인덱스 있을 때: B-Tree 탐색 O(log N)
SELECT *
FROM users
WHERE email = 'kim@gmail.com';
```

#### B-Tree 구조

```
           [김민준]
          /        \
    [미만]           [이상]
    /    \           /    \
[김가나] [김나다] [김바사] [김철수]
```

- 항상 **정렬된 상태** 유지
- 이상/미만으로 트리를 타고 내려가며 탐색 → O(log N)

#### 장단점

| 구분                        | 내용                | 이유              |
|---------------------------|-------------------|-----------------|
| ✅ SELECT 빠름               | O(log N) 탐색       | B-Tree 정렬 상태 유지 |
| ❌ INSERT/UPDATE/DELETE 느림 | 인덱스 B-Tree도 함께 갱신 | 인덱스 10개면 10번 갱신 |

#### Spring / 실무 연결 포인트

| 상황         | 연결                                      |
|------------|-----------------------------------------|
| JPA N+1 문제 | 인덱스 없으면 매번 Full Scan 발생                 |
| 장애 상황      | 인덱스 없는 컬럼 조회 → Full Scan → 쿼리 지연 → 타임아웃 |
| 인덱스 과다     | 쓰기 많은 테이블에 인덱스 남발 → INSERT 성능 저하        |

## 면접 예상 질문 & 모범 답안

### Q1. 인덱스란 무엇이고 왜 사용하나요?

> **모범 답안**
>
> 인덱스는 DB에서 데이터를 빠르게 조회하기 위한 별도의 자료구조입니다.
> 인덱스가 없으면 조건에 맞는 데이터를 찾기 위해 테이블 전체를 탐색하는 Full Scan이 발생하고 O(N)의 시간이 걸립니다.
> 반면 인덱스를 사용하면 B-Tree 구조로 정렬된 상태를 유지하기 때문에 O(log N)으로 탐색이 가능합니다.
> 책의 목차와 동일한 개념으로, 원하는 내용을 찾을 때 처음부터 읽는 대신 목차에서 페이지를 찾아 바로 이동하는 것과 같습니다.

---

### Q2. B-Tree 인덱스가 O(log N)으로 탐색 가능한 이유는 무엇인가요?

> **모범 답안**
>
> B-Tree는 항상 정렬된 상태를 유지하는 트리 자료구조입니다.
> 각 노드에서 현재 값보다 작으면 왼쪽, 크면 오른쪽으로 이동하며 탐색합니다.
> 한 번 비교할 때마다 탐색 범위가 절반씩 줄어들기 때문에 O(log N)이 됩니다.
> 예를 들어 100만 건의 데이터가 있어도 약 20번의 비교만으로 원하는 값을 찾을 수 있습니다.

---

### Q3. 인덱스가 많을수록 좋은 거 아닌가요? 어떤 상황에서 인덱스가 오히려 독이 될 수 있나요?

> **모범 답안**
>
> 인덱스가 많으면 SELECT 성능은 좋아지지만 INSERT / UPDATE / DELETE 성능이 저하됩니다.
> 데이터가 변경될 때마다 관련된 모든 인덱스의 B-Tree를 함께 갱신해야 하기 때문입니다.
> 예를 들어 인덱스가 10개인 테이블에 INSERT가 발생하면 10개의 B-Tree를 모두 갱신해야 합니다.
> 따라서 쓰기 작업이 많은 테이블에 인덱스를 남발하면 오히려 전체 성능이 떨어질 수 있습니다.
> 실무에서는 조회 빈도가 높고 카디널리티(중복도)가 낮은 컬럼에 인덱스를 설정하는 것이 좋습니다.
