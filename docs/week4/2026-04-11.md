## 격리수준 4단계

| 격리수준             | 발생하는 문제                         |
|------------------|---------------------------------|
| READ UNCOMMITTED | Dirty Read                      |
| READ COMMITTED   | Non-repeatable Read             |
| REPEATABLE READ  | Phantom Read (MySQL InnoDB 기본값) |
| SERIALIZABLE     | 문제 없음 (성능 최하)                   |

> 올라갈수록 정합성 ↑, 성능 ↓

---

## 이상 현상 3가지 — 티켓팅 예시

### 1. Dirty Read (READ UNCOMMITTED)

```
A: 좌석 1번 → HELD 변경 (커밋 안함)
B: 좌석 1번 조회 → HELD로 보임 → 선점 포기
A: 롤백 → 좌석 1번 다시 AVAILABLE

결과: B는 비어있는 좌석을 HELD로 잘못 읽고 포기함
```

### 2. Non-repeatable Read (READ COMMITTED)

```
A: 좌석 1번 조회 → AVAILABLE 확인
B: 좌석 1번 → HELD 변경 + 커밋
A: 좌석 1번 다시 조회 → HELD로 보임

결과: 같은 트랜잭션 안에서 같은 row를 두 번 읽었는데 값이 달라짐
```

### 3. Phantom Read (REPEATABLE READ)

```
A: 잔여 좌석 전체 조회 → 10개 확인
B: 새 좌석 1개 추가 + 커밋
A: 잔여 좌석 다시 조회 → 11개로 보임

결과: 같은 트랜잭션인데 건수가 달라짐
```

| 현상                  | 무엇이 바뀌는가      |
|---------------------|---------------|
| Dirty Read          | 커밋 안된 데이터를 읽음 |
| Non-repeatable Read | 같은 row의 값이 바뀜 |
| Phantom Read        | 조회되는 건수가 바뀜   |

## SELECT FOR UPDATE + 격리수준 — 티켓팅 연결

```
A: SELECT FOR UPDATE (배타락 획득) → HOLD 확인 → HELD 변경 → 커밋 → 락 해제
B: SELECT FOR UPDATE 시도 → 대기 (A 커밋까지) → 락 획득 → 이미 HELD → 예외 반환
```

- REPEATABLE READ + SELECT FOR UPDATE 조합으로 좌석 중복 선점 방지 (TASK-016)
- `innodb_lock_wait_timeout` 기본값 50초 초과 시 자동 에러 반환

---

## 인덱스 없는 SELECT FOR UPDATE → 락 범위 확대

```
인덱스 없음
→ Full Scan 발생
→ 모든 Row에 락 시도
→ 사실상 Table Lock
→ 다른 요청 전부 대기
→ 타임아웃 → 503 에러
```

> InnoDB는 Row Lock을 걸 때 인덱스를 기준으로 대상 row를 특정한다.
> 인덱스가 없으면 전체 row를 스캔하며 전체에 락을 건다.

**면접 한 줄 요약**
> "인덱스 없는 SELECT FOR UPDATE는 Full Scan → 전체 Row Lock → 동시성 붕괴"

## Deadlock

### 발생 조건 (4가지)

- 자원 공유 / 비선점 / 순환 대기 / 점유 대기

### 티켓팅 시나리오

```
A 트랜잭션: 좌석 1번 락 → 좌석 2번 락 요청 (대기)
B 트랜잭션: 좌석 2번 락 → 좌석 1번 락 요청 (대기)

결과: 순환 대기 → MySQL이 한쪽 강제 롤백
```

### 해결법

```java
// 좌석 ID를 항상 오름차순 정렬 후 락 획득
seats.sort(Comparator.comparing(Seat::getId));
```

> 모든 트랜잭션이 동일한 순서로 락 획득 → 순환 대기 발생 안함

## TPS 계산 (숫자 기반)

```
TPS = (1000ms / 트랜잭션ms) × maxPoolSize
    = (1000 / 300) × 10
    = 약 33 TPS
```

### 실무 연결

```
티켓 오픈 순간 QPS 200 유입
→ 처리 가능 TPS 33
→ 167개 요청 대기
→ connectionTimeout 초과
→ 503 에러 대량 발생
```

### 해결 방향

1. 트랜잭션 범위 최소화 → 300ms → 100ms → TPS 100 (3배 향상)
2. maxPoolSize 증가 → 단, CPU/DB 한계 고려 필요
