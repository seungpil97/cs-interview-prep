# 2026-04-07 | 트랜잭션 ACID / 격리수준

---

## 1. 트랜잭션이란

하나의 작업 단위 — 전부 성공하거나 전부 실패해야 함

---

## 2. ACID

| 속성 | 이름                | 설명                            |
|----|-------------------|-------------------------------|
| A  | Atomicity (원자성)   | 전부 성공 or 전부 실패, 중간 실패 시 전체 롤백 |
| C  | Consistency (일관성) | 트랜잭션 전후로 데이터 규칙이 깨지면 안됨       |
| I  | Isolation (격리성)   | 동시에 실행 중인 트랜잭션끼리 서로 영향 안줌     |
| D  | Durability (지속성)  | 커밋되면 시스템 장애가 나도 데이터 유지        |

---

## 3. 격리수준 4단계

> 격리성 ↑ → 성능 ↓ 트레이드오프 때문에 4단계로 나눔

```
낮음 ←————————————————→ 높음
READ          READ      REPEATABLE   SERIALIZABLE
UNCOMMITTED   COMMITTED    READ
(성능 최고)                           (성능 최저)
```

| 격리수준             | Dirty Read | Non-repeatable Read | Phantom Read      |
|------------------|------------|---------------------|-------------------|
| READ UNCOMMITTED | ❌ 발생       | ❌ 발생                | ❌ 발생              |
| READ COMMITTED   | ✅ 방지       | ❌ 발생                | ❌ 발생              |
| REPEATABLE READ  | ✅ 방지       | ✅ 방지                | ❌ 발생 (InnoDB는 방지) |
| SERIALIZABLE     | ✅ 방지       | ✅ 방지                | ✅ 방지              |

---

## 4. 발생 가능한 문제 3가지

### Dirty Read

커밋 안된 데이터를 읽는 것

```
A: 재고 10개 → 5개로 수정 (커밋 안함)
B: 재고 조회 → 5개 읽음
A: 롤백 → 재고 다시 10개
B는 존재하지 않는 5개를 읽은 것 💥
```

해결: READ COMMITTED 이상으로 올리기

### Non-repeatable Read

같은 행을 두 번 읽었는데 값이 바뀌는 것

```
A: 재고 조회 → 10개
B: 재고 5개로 수정/커밋
A: 재고 다시 조회 → 5개 💥
```

해결: REPEATABLE READ 이상으로 올리기

### Phantom Read

같은 조건으로 조회했는데 행 수가 바뀌는 것

```
A: 가격 1000원 이하 상품 조회 → 3개
B: 가격 900원 상품 INSERT/커밋
A: 가격 1000원 이하 상품 다시 조회 → 4개 💥
```

해결: SERIALIZABLE or 명시적 락 (SELECT FOR UPDATE)

## 5. 실무 선택 기준

| 상황        | 격리수준            | 이유             |
|-----------|-----------------|----------------|
| 일반적인 서비스  | REPEATABLE READ | 기본값, 성능/정합성 균형 |
| 읽기 많은 서비스 | READ COMMITTED  | 성능 우선          |
| 결제/금융     | SERIALIZABLE    | 강한 정합성 필요      |

MySQL InnoDB 기본값 = **REPEATABLE READ**

## 7. MVCC 맛보기 (다음 주차 예고)

격리수준으로 읽기를 보호할 때 B는 A를 기다리지 않음
→ InnoDB가 **Undo Log에 수정 전 원본을 보관**해서 이전 버전을 바로 읽어옴
→ 락 없이 읽기 가능 = **MVCC (Multi Version Concurrency Control)**

| 방식   | 동작             | 성능 |
|------|----------------|----|
| 락    | B가 A 끝날 때까지 대기 | 느림 |
| MVCC | B가 이전 버전 바로 읽음 | 빠름 |

---

## 8. 트랜잭션 격리수준이 무엇인지, 왜 4단계로 나뉘는지 설명

> "격리수준은 트랜잭션끼리 서로 영향을 얼마나 차단할지 정하는 기준입니다.
> 격리성을 높이면 정합성은 올라가지만 성능이 떨어지는 트레이드오프가 있어서 4단계로 나눠 상황에 맞게 선택합니다.
> READ UNCOMMITTED부터 SERIALIZABLE까지 있고, 단계가 낮을수록 Dirty Read, Phantom Read 같은 문제가
> 발생합니다.
> 실무에서는 성능과 정합성 균형이 맞는 REPEATABLE READ를 기본으로 씁니다."

## 9. 오늘 질문

**Q1. 트랜잭션 ACID에서 Isolation이 무엇인지 설명하세요.**

> "Isolation은 동시에 실행 중인 트랜잭션끼리 서로 영향을 주지 않도록 격리하는 성질입니다. 격리성을 높이면 정합성은 올라가지만 성능이
> 떨어지는 트레이드오프가 있어서 4단계 격리수준으로 나눠 상황에 맞게 선택합니다."

---

**Q2. Dirty Read, Non-repeatable Read, Phantom Read의 차이를 설명하세요.**

> "Dirty Read는 커밋되지 않은 데이터를 읽는 문제입니다. Non-repeatable Read는 같은 행을 두 번 읽었는데 중간에
> UPDATE가 발생해서 값이 바뀌는 문제입니다. Phantom Read는 같은 조건으로 조회했는데 중간에 INSERT/DELETE가 발생해서
> 행
> 수가 달라지는 문제입니다."

---

**Q3. 실무에서 격리수준을 REPEATABLE READ로 두는 이유는 무엇인가요?**

> "REPEATABLE READ는 Dirty Read와 Non-repeatable Read를 방지하면서 성능도 준수해서 균형이 맞기
> 때문입니다. SERIALIZABLE은 정합성은 완벽하지만 모든 트랜잭션을 순차 실행하는 수준이라 성능이 너무 떨어져 실무에서 잘 쓰지
> 않습니다.
> MySQL InnoDB는 MVCC로 Phantom Read까지 대부분 방지해줘서 REPEATABLE READ가 기본값으로 적합합니다."
