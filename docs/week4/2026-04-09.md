# 2026-04-09 | Lock 기초

## 오늘 학습 요약

**한 줄 요약:** Lock은 쓰기 충돌을 직렬화하며, 인덱스 설계가 락 범위를 결정한다.

**프로젝트 연결 (TASK-016)**

- `PESSIMISTIC_WRITE` → `SELECT ... FOR UPDATE` → Row Lock → Deadlock 없음
- `showtime_id`, `seat_id` 인덱스 덕분에 Row Lock으로 동작
- 인덱스 없었으면 Full Scan → Table Lock 수준 → 동시성 폭락

---

## 핵심 개념

### 공유락 vs 배타락

| 구분        | 공유락 (S Lock)                    | 배타락 (X Lock)            |
|-----------|---------------------------------|-------------------------|
| SQL       | `SELECT ... LOCK IN SHARE MODE` | `SELECT ... FOR UPDATE` |
| JPA       | `PESSIMISTIC_READ`              | `PESSIMISTIC_WRITE`     |
| 다른 S Lock | ✅ 허용                            | ❌ 차단                    |
| 다른 X Lock | ❌ 차단                            | ❌ 차단                    |
| 목적        | 읽는 동안 수정 금지                     | 수정할 거니까 접근 전부 금지        |

### Row Lock vs Table Lock

| 구분    | Row Lock        | Table Lock                  |
|-------|-----------------|-----------------------------|
| 락 범위  | 해당 Row만         | 테이블 전체                      |
| 동시성   | 높음              | 낮음                          |
| 발생 조건 | 인덱스 있는 컬럼 WHERE | 인덱스 없는 컬럼 WHERE (Full Scan) |

### Deadlock 4가지 조건

1. **상호 배제** — 자원은 한 번에 하나만 사용 가능
2. **점유와 대기** — 락 보유한 채로 다른 락 대기
3. **비선점** — 락을 강제로 빼앗을 수 없음
4. **순환 대기** — A→B 대기, B→A 대기 (핵심!)

**해결책:** 락 획득 순서 통일 → 순환 대기 불가능

### 인덱스 ↔ 락 연결

```
[인덱스 있음]
WHERE 조건 → B-Tree 탐색 → 해당 Row만 → Row Lock → 동시성 높음

[인덱스 없음]
WHERE 조건 → Full Scan → 전체 Row 탐색 → Table Lock 수준 → 동시성 폭락
```

## Q&A

### Q1. 공유락과 배타락의 차이는?

**모범답안:**
공유락(S Lock)은 읽는 동안 다른 트랜잭션의 수정을 막지만, 다른 공유락은 허용합니다. 배타락(X Lock)은 읽기/쓰기 모두 차단해서
단독 접근을 보장합니다. SQL에서는 각각 `LOCK IN SHARE MODE`, `FOR UPDATE`로 실행되고,
JPA에서는 `PESSIMISTIC_READ`, `PESSIMISTIC_WRITE`로 매핑됩니다.

---

### Q2. Deadlock 4가지 조건은?

**모범답안:**
상호 배제, 점유와 대기, 비선점, 순환 대기 4가지 조건이 모두 충족될 때 발생합니다. 가장 핵심은 순환 대기인데, A가 B를 기다리고 B가
A를 기다리는 상황입니다. 해결책은 모든 트랜잭션이 동일한 순서로 락을 획득하도록 강제해서 순환 대기 자체를 불가능하게 만드는 겁니다.

---

### Q3. 인덱스 없는 컬럼에 `FOR UPDATE`를 날리면 어떻게 되나요?

**모범답안:**
인덱스가 없으면 B-Tree 탐색이 불가능해서 Full Scan이 발생합니다. Full Scan 과정에서 탐색한 모든 Row에 락을 걸게 되어
사실상 Table Lock 수준의 락 범위가 됩니다. 결과적으로 해당 테이블에 접근하는 다른 트랜잭션이 전부 대기하게 되어 동시성이 크게
저하됩니다. 실무에서는 이 때문에 인덱스 설계를 성능뿐 아니라 락 범위 최소화 차원에서도 반드시 고려해야 합니다.

---

### Q4. (Cross) Deadlock이 발생했을 때 MySQL은 어떻게 처리하나요?
모범답안:
MySQL InnoDB는 Deadlock을 자동으로 감지합니다. 순환 대기가 감지되면 트랜잭션 중 하나를 강제 롤백시키고 ERROR 1213:
Deadlock found when trying to get lock을 반환합니다. 일반적으로 롤백 비용이 적은 트랜잭션을 희생자로 선택합니다.
SHOW ENGINE INNODB STATUS로 가장 최근 발생한 Deadlock 히스토리를 확인할 수 있습니다. 애플리케이션에서는 이 예외를
잡아서 재시도 로직을 구성하거나, 근본적으로는 락 획득 순서를 통일해서 Deadlock 자체를 예방하는 게 맞습니다.

---

### Q5. (숫자) Lock 대기 평균 500ms, `maxPoolSize=10`이면 TPS는 몇이고, QPS 50이 들어오면 어떤 일이 발생하나요?

**모범답안:**
TPS = (1000ms / 500ms) × 10 = **초당 20 TPS**입니다. QPS 50이 들어오면 매 초 30개 요청이 처리되지
못하고 대기 큐에 쌓입니다. 대기 시간이 `connectionTimeout`(기본 30초)을
초과하면 `Connection is not available, request timed out` 예외가 발생하고 사용자는 503 에러를 받게
됩니다. 해결 방법은 Lock 대기 시간 단축(트랜잭션 범위 최소화), maxPoolSize 조정, 또는 Redis 분산락으로 DB 락 의존도
낮추는 방향입니다.

## ❗ 사용하면 안 되는 경우

| 상황              | 이유                                   |
|-----------------|--------------------------------------|
| 읽기 위주 트래픽       | 락 오버헤드 → MVCC로 충분                    |
| 긴 트랜잭션 안에서 Lock | 락 대기 → 커넥션 풀 고갈                      |
| 인덱스 없는 컬럼에 Lock | Row Lock → Table Lock 수준 확대 → 동시성 폭락 |
