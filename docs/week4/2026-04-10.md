## 1. 개념 정리

### MVCC (Multi-Version Concurrency Control)

**등장 배경:**
Lock 기반 DB에서는 쓰기가 진행 중이면 읽기도 대기해야 했다.
QPS 1000 서비스에서 SELECT마다 대기하면 처리량이 급감한다.
→ "읽기는 절대 막지 말자"는 원칙으로 MVCC 등장

**정의:**
데이터 수정 시 이전 버전을 Undo Log에 보관해,
읽기 트랜잭션이 락 없이 이전 버전을 조회할 수 있게 하는 메커니즘

**내부 동작:**

```
트랜잭션 A: 좌석 AVAILABLE → HELD 로 UPDATE
  └─ 현재 row: HELD (X락 보유)
  └─ Undo Log: AVAILABLE (이전 버전 보관)

트랜잭션 B: SELECT
  └─ X락 대기 안 함
  └─ Read View 기준으로 Undo Log에서 AVAILABLE 읽음
```

---

### Undo Log

- 데이터 수정 시 이전 버전을 보관하는 공간
- 트랜잭션 롤백 시에도 사용됨
- 버전 체인: 수정이 여러 번 일어나면 버전이 연결 리스트처럼 쌓임

---

### Read View

- 트랜잭션이 "어느 시점의 데이터까지 볼 수 있는가"를 결정하는 스냅샷
- Read View 기준으로 Undo Log에서 적절한 버전을 선택해 읽음

**격리수준에 따른 Read View 생성 시점:**

| 격리수준            | Read View 생성 시점 | 결과                |
|-----------------|-----------------|-------------------|
| READ COMMITTED  | 매 SELECT마다 생성   | 커밋된 최신 데이터 읽음     |
| REPEATABLE READ | 트랜잭션 시작 시 1번 생성 | 트랜잭션 내내 같은 스냅샷 읽음 |

---

### Phantom Read

**정의:**
같은 조건으로 두 번 조회했을 때 row 개수가 달라지는 현상

**발생 이유:**

```
기존 row (UPDATE)
  └─ Undo Log에 이전 버전 있음 → Read View로 걸러낼 수 있음

새로 INSERT된 row
  └─ Undo Log에 이전 버전이 아예 없음
  └─ Read View가 걸러낼 버전 체인 자체가 없음
  └─ Read View 이후 INSERT인데도 보여버림 → Phantom Read
```

**실무에서 문제가 되는 경우:**
단순 읽기는 큰 문제 없지만, **읽은 결과로 쓰기를 결정하는 구조**에서 정합성이 깨진다.

```
1. 잔여 좌석 조회 → 10개 (Read)
2. "10개니까 예약 가능" 판단 (Decision)
3. 예약 INSERT (Write)
   ← 이 사이에 누군가 좌석 INSERT
4. 다시 잔여 좌석 확인 → 11개 (Phantom Read)
5. 로직이 "10개 기준"으로 짜여 있어서 정합성 깨짐
```

**Non-repeatable Read vs Phantom Read 비교:**

| 현상                  | 원인             | 내용                           |
|---------------------|----------------|------------------------------|
| Non-repeatable Read | 기존 row UPDATE  | 같은 row를 두 번 읽었는데 값이 달라짐      |
| Phantom Read        | 새로운 row INSERT | 같은 조건으로 두 번 읽었는데 row 개수가 달라짐 |

---

### SELECT FOR UPDATE와 MVCC 관계

**일반 SELECT:**

```
MVCC 경로 → Undo Log에서 스냅샷 버전 읽기
→ 락 없음, 대기 없음, 근데 오래된 버전일 수 있음
```

**SELECT FOR UPDATE:**

```
MVCC 우회 → 현재 실제 row에 X락 획득
→ 다른 트랜잭션이 수정 중이면 대기
→ 락 풀리면 최신 데이터 읽음
```

SELECT FOR UPDATE는 **쓰기 의도를 가진 조회**이기 때문에 MVCC를 우회하고 현재 실제 데이터에 락을 잡는다.

---

### MVCC vs Lock 비교표

| 항목    | MVCC              | Lock               |
|-------|-------------------|--------------------|
| 읽기 방식 | Undo Log 이전 버전 조회 | 현재 데이터 직접 조회       |
| 읽기 대기 | 없음 (Non-blocking) | S락 필요, X락과 충돌 시 대기 |
| 정합성   | 격리수준에 따라 다름       | 강한 정합성 보장          |
| 언제 선택 | 읽기 위주 트래픽         | 결제/예약 같은 강한 정합성 필요 |

## 2. 프로젝트 연결

### TASK-016 → TASK-019 흐름

| 문제       | 원인                                        | 해결                           |
|----------|-------------------------------------------|------------------------------|
| 중복 HOLD  | MVCC가 이전 버전 읽음 → AVAILABLE로 보이지만 실제론 HELD | SELECT FOR UPDATE (TASK-016) |
| 락 범위 과대  | 인덱스 없어서 Full Scan → 불필요한 row에도 락          | 인덱스 추가 (TASK-017)            |
| DB 부하 집중 | 락 대기 중 DB 커넥션 점유 → maxPoolSize 소진         | Redis 분산락 (TASK-019)         |

### 장애 시나리오

**MVCC를 믿고 일반 SELECT로 좌석 상태 확인한 경우:**

```
트랜잭션 A: 좌석 1번 HOLD 중 (X락 보유)
트랜잭션 B: SELECT → Undo Log → AVAILABLE로 읽음
→ HOLD 생성 시도 → 중복 HOLD 발생
```

**비관적 락 대기 중 커넥션 풀 고갈:**

```
티켓 오픈 순간 100명 동시 요청
→ 1명 락 획득, 99명 FOR UPDATE 대기
→ 99개 커넥션이 락 풀릴 때까지 점유
→ maxPoolSize=10이면 89개 요청은 connectionTimeout → 503
```

## 3. ❗ MVCC 사용하면 안 되는 경우

| 상황                             | 이유                       |
|--------------------------------|--------------------------|
| 최신 데이터가 반드시 필요한 경우 (좌석 선점, 결제) | Undo Log 버전 읽어서 정합성 깨짐   |
| 읽은 결과로 쓰기를 결정하는 구조             | Phantom Read로 데이터 정합성 오염 |

## 4. 면접 Q&A

---

### Q1. MVCC가 무엇인지 한 줄로 설명하세요.

**모범 답안:**

MVCC는 데이터 수정 시 이전 버전을 Undo Log에 보관해, 읽기 트랜잭션이 락 없이 이전 버전을 조회할 수 있게 하는 메커니즘입니다.

Lock 기반에서는 쓰기가 진행 중이면 읽기도 대기해야 해서 처리량이 급감하는 문제가 있었고, MVCC는 이를 해결하기 위해 등장했습니다.

내부적으로는 트랜잭션 시작 시 Read View를 생성하고, SELECT 시 Undo Log에서 Read View 기준으로 커밋된 버전을
읽습니다.

주의할 점은 최신 데이터가 반드시 필요한 경우, 예를 들어 좌석 선점처럼 AVAILABLE 여부를 정확히 확인해야 하는 상황에서는 Undo
Log 버전을 읽으면 이미 HELD인 좌석을 AVAILABLE로 읽어 중복 예약이 발생합니다. 그래서 SELECT FOR UPDATE를 씁니다.

---

### Q2. READ COMMITTED와 REPEATABLE READ에서 Read View 생성 시점이 어떻게 다른가요?

**모범 답안:**

READ COMMITTED는 매 SELECT마다 Read View를 생성합니다. 그래서 조회할 때마다 그 시점의 최신 커밋 데이터를 읽을 수
있습니다.

REPEATABLE READ는 트랜잭션 시작 시 딱 1번 Read View를 생성합니다. 그래서 트랜잭션 내내 같은 스냅샷을 읽어 일관성이
보장됩니다.

MySQL InnoDB의 기본값은 REPEATABLE READ이고, 티켓팅 프로젝트도 이 격리수준을 사용합니다.

---

### Q3. 좌석 선점에서 일반 SELECT 대신 SELECT FOR UPDATE를 쓴 이유가 무엇인가요?

**모범 답안:**

일반 SELECT는 MVCC 경로를 타서 Undo Log의 이전 버전을 읽습니다. 다른 트랜잭션이 좌석을 HELD로 수정 중이어도 이전 버전인
AVAILABLE을 읽어버려서 중복 HOLD가 발생합니다.

SELECT FOR UPDATE는 쓰기 의도를 가진 조회라서 MVCC를 우회하고 현재 실제 row에 X락을 획득해 최신 데이터를 읽습니다.

이렇게 하면 먼저 락을 획득한 트랜잭션이 커밋될 때까지 다른 트랜잭션은 대기하고, 락 해제 후 HELD 상태를 확인해 예외 처리하므로 중복
선점을 막을 수 있습니다. (TASK-016)

---

### Q4. (Cross) REPEATABLE READ에서 MVCC가 동작하는데, 왜 좌석 선점에서는 MVCC만으로 정합성을 보장할 수 없나요?

**모범 답안:**

MVCC는 읽기에서 이전 버전을 보여주는 것이고, 정합성 보장은 별개의 문제입니다.

REPEATABLE READ에서 좌석 선점 흐름을 보면:

1. 트랜잭션 B: SELECT → Undo Log → AVAILABLE (Read View 기준)
2. 트랜잭션 A: 이미 같은 좌석 HELD로 변경 + COMMIT
3. 트랜잭션 B: AVAILABLE로 읽었으니 HOLD 생성 → 중복 발생

MVCC는 "읽기 성능"을 위한 메커니즘이고, "정합성 보장"은 Lock의 역할입니다.

좌석 선점처럼 읽은 결과로 쓰기를 결정하는 구조에서는 반드시 SELECT FOR UPDATE로 현재 실제 데이터를 락 잡고 읽어야 합니다.

정리하면, MVCC는 읽기 처리량을 높이고 Lock은 쓰기 정합성을 보장하는 역할로, 둘은 대체 관계가 아니라 보완 관계입니다.

### Q5. (숫자 기반) maxPoolSize=10, 락 대기 평균 500ms 상황에서 QPS 100이 들어오면 어떤 현상이 발생하나요?

**모범 답안:**

계산식:

```
초당 처리량 = (1000ms / 500ms) × 10개 = 초당 20 TPS
QPS 100 유입 → 80개 요청은 커넥션 대기
connectionTimeout(기본 30초) 내에 처리 못하면 예외
```

현상 순서:

1. 락 대기 중인 트랜잭션들이 커넥션을 점유한 채 반납 안 함
2. HikariCP active connections = maxPoolSize 상태 지속
3. 새 요청은 커넥션 대기 → connectionTimeout 초과
4. "Connection is not available, request timed out" 로그 발생
5. 503 에러 대량 발생

해결 방향:

- maxPoolSize 증가 (단기)
- 트랜잭션 범위 최소화로 커넥션 점유 시간 단축 (근본)
- Redis 분산락으로 전환해 DB 커넥션 외부에서 락 관리 (TASK-019)

티켓팅처럼 특정 시간에 트래픽이 폭증하는 서비스에서는 비관적 락의 커넥션 점유 문제가 치명적이라서 Redis 분산락으로 전환한 것입니다.
